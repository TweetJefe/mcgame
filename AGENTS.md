# Память проекта: целевая архитектура героев

Согласовано с пользователем 20 октября 2026 года по четырём архитектурным схемам.
Это целевая структура для дальнейшей разработки, а не описание полностью завершённой миграции.

## Главный критерий расширяемости

Пользователь уточнил ожидаемый процесс добавления любого нового героя:

1. Агент пишет героя по заданному шаблону и добавляет относящиеся к нему правила и тесты.
2. Герой регистрируется в реестре.
3. Добавляются его отображение и ресурсы интерфейса.

На этом подключение должно завершаться: без изменений глобальной игровой логики,
`Game`, `ActionEngine` и без ручного добавления обработки конкретного героя в общие
подсистемы. Это основной критерий готовности целевой архитектуры и соблюдения
Open–Closed. Общие контракты должны обеспечивать такой процесс; при проектировании
не считать регулярные правки ядра допустимым способом подключения очередного героя.
Текущий каркас ещё не обеспечивает весь этот процесс; дальнейшую миграцию направлять
на достижение этого требования.

## Поведение и состояние

- `Hero` — Stateless Strategy / Flyweight: один переиспользуемый объект поведения на тип героя
  и конфигурацию правил, без изменяемого состояния конкретной фигуры.
- Правила героя неизменяемы. Состояние фигуры (ID, позиция, кулдаун, заряд ульты,
  проглоченный союзник и прочее) хранится в `PieceState`.
- `HeroActionContext` в `game.heroes` передаёт снимок `Field`, неизменяемую копию
  `Map<Long, PieceState>` и `currentTurn`; предоставляет `pieceAt` и `pieceById`.
  Для проверок и журнала также передаются неизменяемые `TerrainState`, `FaunState`,
  `SpellState` и `EconomyState`. Исходный конструктор из трёх аргументов сохранён.
- Методы героя возвращают новый `PieceState` или неизменяемый `HeroEffect` с предложенными
  изменениями и взятиями. Они не изменяют живую партию, входной контекст, бюджеты или историю.
- Герои с начала партии назначаются подходящим базовым шахматным фигурам: ладье, слону,
  коню и т. д. Назначение выполняется при инициализации партии и сохраняется в `PieceState.hero()`.
  Связь с допустимыми типами фигур уже задаётся через `HeroType.supports(...)`;
  интерфейс `Hero` предоставляет `supports(Class<? extends Figure>)`, и `Game`
  использует его через реестр при назначении героев.

## Контракт и Template Method

Целевой `Hero` предоставляет:

- `type(): HeroType`;
- `abilities(): List<Ability>`;
- `supports(Class<? extends Figure>): boolean`;
- `availability(PieceState, Ability): MoveResult`;
- `preview(HeroActionContext, PieceState actor, PieceState target, Position square, Ability): HeroEffect`;
- `afterCapture(PieceState): PieceState`;
- `targeting(Ability): HeroTargeting` и `requests(...)` для общих проверок целей и поиска действий;
- `onCaptured(...)` для предложения одной реакции на гибель;
- `abilityMessage(...)` для текста журнала успешной способности.

`AbstractHero` реализует общие проверки доступности, кулдауна и заряда ульты,
а также общее начисление заряда за взятия. Неизменяемая конфигурация базы:
`type`, `abilities`, `ultimateAbility`, `ultimateCaptures`.

`preview` — общий шаблон: проверка доступности, затем вызов `previewAvailable(...)`.
Подклассы расширяют `availabilitySpecific(...)` и реализуют `previewAvailable(...)`:
проверяют цели, рассчитывают геометрию и включают стоимость успешной способности
в предлагаемые изменения. Для списания заряда и проверок доступны
`protected final ultimateCaptures()` и `protected final ultimateAbility()`.

Конкретные классы (`PudgeHero`, `BolotnikHero`, `ZeusHero` и последующие)
наследуют `AbstractHero`, содержат собственные неизменяемые `*Rules` и специфику героя.
Стремиться собирать поведение героя в его классе, устраняя дублирование общих проверок.

## Реестр и взаимодействие с ядром

- Целевой `HeroRegistry` в `game.heroes` хранит `Map<HeroType, Hero>` и предоставляет
  `get(HeroType)`, `register(Hero)` и статическую фабрику `fromRules(HeroRules)`.
  Реестр уже реализован неизменяемым: `register` возвращает новый экземпляр,
  повторная регистрация типа или неоднозначный владелец способности отклоняются.
  `Game` создаёт реестр один раз для своих правил; подготовленные контексты сохраняют его.
- `Game` / `ActionEngine` взаимодействуют с интерфейсом `Hero` через реестр,
  не выбирают конкретных героев большими `switch` и не знают деталей их способностей.
- Цепочка действия: UI → `Game` → `ActionEngine` → `registry.get(actor.hero())`
  → `Hero.preview(...)` → общие проверки `AbstractHero` → конкретный
  `previewAvailable(...)` → `HeroEffect` → проверка и подготовка результата ядром
  → публикация успешного состояния через `Game`.
- Добавление героя должно сводиться к его реализации, конфигурации и регистрации;
  не добавлять в ядро новые ветки диспетчеризации по типу героя.
- Конечная цель — полностью заменить процедурный диспетчер `HeroAbilities`
  полиморфными вызовами через `HeroRegistry` и убрать его после миграции вызовов.

## Состояние перехода

`PudgeHero` подключён к игровому пути через `HeroRegistry`: доступность, цели,
хук, проглатывание, проверка болота, начисление заряда, реакция на гибель и сообщения
журнала. `Game` / `ActionEngine` больше не содержат веток `HOOK` / `SWALLOW`;
назначение Пуджа в начальной расстановке остаётся конфигурацией.

`CaptureReactions` — общая ограниченная очередь вызовов `Hero.onCaptured`,
дальнейших гибелей и начисления заряда выжившему исполнителю ответного взятия.
Специфика Пуджа находится в `PudgeHero`. Ginseng с проглоченным союзником
переиспользует ту же реакцию через временный адаптер; порядок реакции Ares сохранён.

`HeroAbilities` и `PudgeAbilities` сохранены как фасады совместимости.
Другие герои временно подключены через `LegacyHero` / `LegacyHeroAbilities`;
часть их активных механик и метаданных событий ещё остаётся в ядре.
Переход всей системы на критерий «шаблон + регистрация + отображение» ещё не завершён.
Мигрировать остальных героев поэтапно, без новых веток по мигрированному герою в ядре.
Подробности: [docs/HERO_MIGRATION.md](docs/HERO_MIGRATION.md).

## Рабочая исходная точка и сохранение поведения

20 октября 2026 года восстановлены функциональные изменения, потерянные при merge
`3788fee`, по проверенному родительскому коммиту `f624241`. На момент восстановления
существующий Java-код совпадал с эталоном по исполняемым токенам; новые ООП-классы сохранены.
Исправлена только тестовая прокрутка каталога в шести UI-тестах драфта.

Исходный прогон после восстановления: 610 тестов (568 Java + 42 UI),
без падений и пропусков. Подробности и границы восстановления:
[docs/BUILD_BASELINE.md](docs/BUILD_BASELINE.md).

После подключения Пуджа `bash gradlew :composeApp:jvmTest` проходит: 617 тестов
(575 Java + 42 UI), без падений и пропусков. С версией до подключения также совпали
1371 запись сравнения результатов, целей и сохранений на пяти сценариях Пуджа.

Пользователь требует сохранять игровое поведение при улучшении структуры:
доступность и причины отказов, цели, перемещения, взятия и реакции, стоимость,
заряд и кулдауны, состояние и историю партии, совместимость сохранений.
Не смешивать перенос на новый контракт с изменениями правил или исправлением
игровых ошибок. Подключение полного контракта Пуджа через реестр выполнено;
дальнейшие изменения должны переносить других героев и оставшиеся общие механизмы.
