# Как создавать и переносить героев

Обязательный контракт создания и переноса героя. Общие правила кода:
[AGENTS.md](AGENTS.md).

## 1. Границы ответственности

Подключение героя состоит из реализации по этому контракту, регистрации,
добавления отображения и ресурсов. Поведение героя не должно требовать веток
по его типу или способностям в `Game`, `ActionEngine` и общих обработчиках.
При переносе существующего героя сохранять его игровые правила и наблюдаемые результаты.

Агент, реализующий героя, использует общий контракт и не меняет его в рамках
переноса одного героя. Изменения общих API проектируются отдельной задачей.
Пример реализации: [PudgeHero](../composeApp/src/jvmMain/java/game/heroes/pudge/PudgeHero.java).

## 2. Файлы и ответственность

```text
composeApp/src/jvmMain/java/game/heroes/<имя>/
  <Name>Ability.java       enum: идентичность, подпись, политика целей, список
  <Name>Rules.java         неизменяемые параметры баланса
  <Name>Hero.java          final class extends AbstractHero: правила и эффекты
  <Name>Definition.java    HeroDefinition<Rules>: описание и фабрика стратегии
  <Name>RulesCodec.java    явное чтение и запись параметров героя
  <Name>StatePolicy.java   инициализация и собственные ограничения состояния
  <Name>Mechanic.java      модуль собственной механики, если он необходим
composeApp/src/jvmTest/java/game/heroes/<имя>/
  <Name>HeroTest.java      проверки игрового поведения
composeApp/src/jvmMain/kotlin/org/chess/heroes/<имя>/
  <Name>Presentation.kt   карточка, значок, подсказки и локальные виджеты
```

Дополнительные типы в пакете нужны только для самостоятельных понятий механики.
Геометрию и выбор операций реализовать в `<Name>Hero`; состояние и обработчики
самостоятельной механики — в её модуле. Не создавать статический `<Name>Abilities`
с отдельной реализацией поведения или диспетчеризацией.
Поведение предоставляют `Hero` и реестр. Предпросмотр вызывается только через
`preview(HeroActionContext, AbilityRequest)`; исполнитель и цель извлекаются из
контекста. Не создавать статические фасады способностей или перегрузки предпросмотра с отдельно
переданными `PieceState`. В тестах передавать актуальные состояния в карту контекста.

`Hero` — переиспользуемая стратегия. Две фигуры одного героя могут пользоваться
одним объектом поведения и иметь совершенно разные состояния.
`PieceState` хранит ID, текущую шахматную форму, героя, позицию, статусы и ресурсы фигуры.
Не хранить эти значения в полях стратегии.

Герой назначается совместимой шахматной фигуре в начале игры; это не наследование
`Hero` от `Rook`, `Bishop` и т. п. Допустимые начальные фигуры задаются в
`HeroDefinition.supportedBodies()`. `Hero.supports` использует это описание.
`HeroType` хранит только идентичность героя (`PUDGE`, `ZEUS`, `GINSENG`),
без суффикса шахматной фигуры, отображаемого названия и правил совместимости.
Проверка назначения проходит через реестр.
Превращение фигуры и копирование способности имеют собственные правила:
не назначать героя заново при каждом действии по текущему классу фигуры.

## 3. Enum способностей

Каждый герой объявляет собственный `enum <Name>Ability implements Abilities`.
Интерфейс требует `id()` и `getDisplayName()`; `targeting()` имеет реализацию
по умолчанию. В enum явно задать политику каждой способности.
`eventTarget()` задаёт наличие идентификатора цели в записи успешного применения.

Пример устройства на существующем Пудже:

```java
public enum PudgeAbility implements Abilities {
    HOOK("HOOK", "Хук", HeroTargeting.square(
            HeroTargeting.Permission.ILLUSION, HeroTargeting.Permission.POTTED)),
    SWALLOW("SWALLOW", "Проглотить", HeroTargeting.square());

    private static final List<Abilities> ABILITIES = Abilities.getAbilities(values());

    private final String id;
    private final String displayName;
    private final HeroTargeting targeting;

    PudgeAbility(String id, String displayName, HeroTargeting targeting) {
        this.id = id;
        this.displayName = displayName;
        this.targeting = targeting;
    }

    public static List<Abilities> getAbilities() { return ABILITIES; }
    @Override public String id() { return id; }
    @Override public String getDisplayName() { return displayName; }
    @Override public HeroTargeting targeting() { return targeting; }
}
```

В файле нужны импорты `game.heroes.Abilities`, `game.heroes.HeroTargeting`, `java.util.List`.
Список создаётся один раз, неизменяем и сохраняет порядок объявления.
Новая константа автоматически входит в список: вручную перечислять её в герое не нужно.
Статический `getAbilities()` — договорённость для enum. Java не позволяет требовать
переопределения статического метода интерфейса; `Abilities.getAbilities(values())`
является общей фабрикой списка.

ID — явный стабильный ключ сохранений, уникальный среди всех зарегистрированных
способностей. Не выводить его из `ordinal()`, `name()` или отображаемого текста.
Прежние ID не переименовывать.

### Политика целей

`HeroTargeting` явно задаёт схему выбора через `selection()`:

- `untargeted()` / `NONE` — без цели;
- `square(...)` / `SQUARE` — одна клетка `target`;
- `targetAndDestination(...)` / `TARGET_AND_DESTINATION` — сначала `target`, затем `destination`.

`requiresTarget()` и `requiresDestination()` выводятся из этой схемы.
Разрешения целей: `SELF`, `KING`, `INVISIBLE`, `POTTED`, `BOXED`, `ILLUSION`.
Без соответствующего разрешения общая проверка отклоняет такой запрос.
Не определять количество этапов по ID способности или по наличию доступных целей.

Политика не задаёт дальность, препятствия, дружественность цели и требование
занятой/пустой клетки. Всё это проверяет конкретный герой.
`HeroTargeting.validate` может успешно проверить пустую клетку: это не означает,
что любая способность может применяться туда.
Порядок общих причин отказа сохранять при миграции.

## 4. Описание, Rules и конструктор героя

`<Name>Rules` — неизменяемый record или класс с валидацией параметров.
Числа баланса хранить здесь; стратегия получает правила через конструктор.
Не брать `prototype()` внутри каждого игрового вызова: использовать правила партии.

### HeroDefinition

В `<Name>Definition` объявить одну `public static final HeroDefinition<<Name>Rules> INSTANCE`.
Описание содержит `HeroType`, отображаемое название, неизменяемый набор совместимых
начальных шахматных фигур, `Class<Rules>`, стандартные параметры, кодек, фабрику
стратегии и неизменяемую `HeroStatePolicy<Rules>`.
Чтение описания не создаёт стратегию и не зависит от состояния партии.
Последний необязательный аргумент конструктора — `List<MechanicDefinition<?>>`:
передать здесь модули механик, используемых героем. Отсутствие аргумента означает
пустой список зависимостей. Реестр собирает модули автоматически; отдельный
центральный список для новой механики не изменять.

```java
public static final HeroDefinition<PudgeRules> INSTANCE = new HeroDefinition<>(
        HeroType.PUDGE, "Пудж-Ладья", Set.of(Rook.class),
        PudgeRules.class, PudgeRules.prototype(), new PudgeRulesCodec(), PudgeHero::new,
        List.of(SwallowMechanic.INSTANCE))
        .withStatePolicy(new PudgeStatePolicy())
        .withDraftProfile(DraftProfile.pickable(1));
```

Фабрика получает параметры своего героя и создаёт его `<Name>Hero`.
`hero.definition()` должен возвращать именно это описание. Передать `INSTANCE`
в конструктор `AbstractHero`, чтобы база предоставляла `definition()` и `type()`.

### Доступность в драфте

`HeroDefinition.draftProfile()` задаёт участие в новых каталогах и порядок.
При объявлении `INSTANCE` использовать `.withDraftProfile(DraftProfile.pickable(order))`
для героя, доступного в пиках. Метод возвращает новое описание; регистрацию и
`HeroRules` создавать после окончательного объявления `INSTANCE`.
`DraftProfile.EXCLUDED` — стандартное значение для обычных и призываемых сущностей.
Порядок определяется `order`, затем стабильным ID. Не использовать `enum.ordinal()`.

Новый каталог собирается из зарегистрированных описаний конкретной конфигурации.
Клетки назначения выводятся из `supportedBodies()` на стандартной начальной доске.
Не добавлять героя в отдельный список `HeroCatalog` или `switch` размещения.
`DraftSnapshot.catalog()` фиксирует состав и порядок; последующие действия и
восстановление используют этот снимок, без автоматического расширения состава.

### Инициализация и ограничения состояния

`<Name>StatePolicy implements HeroStatePolicy<<Name>Rules>` подключается при объявлении
описания через `.withStatePolicy(new <Name>StatePolicy())`. Этот метод, как и
`withDraftProfile`, возвращает новое описание: завершить объявление до регистрации.
Политика не хранит фигуры, контексты или изменяемые данные партии.

| Метод | Обязательство |
| --- | --- |
| `initialize(base, origin, rules)` | Подготовить собственные начальные поля героя и вернуть новый `PieceState` |
| `validate(piece, rules)` | Проверить допустимую текущую форму, собственные поля и пределы ресурсов |
| `validateOrigin(piece, square, rules)` | Проверить связь с исходной клеткой, если герой её хранит |

`rules` — параметры описания из реестра текущей партии. Не использовать стандартные
параметры вместо переданных. `HeroStateConstraints` переиспользует проверки форм,
исходного цвета, разрешений болота, хранения проглоченной фигуры и растворения,
а также пределов кулдауна и заряда. Специфические правила дописывать локально.

`HeroDefinition.supportedBodies()` ограничивает **начальное назначение**.
Политика проверяет **формы во время игры**: например, пешечный герой сохраняет
личность после превращения. Не проверять каждое обновление через `Hero.supports`.
Допустимые формы и специальные поля объявлять в локальной политике, без добавления
списков `HeroType` в `PieceState`, фабрику или общие валидаторы.

Создавать начальное состояние через `new HeroPieceFactory(registry).initial(id, figure, hero)`.
Призыв и превращение используют `factory.create(base, origin)`: вызывающий модуль
явно формирует базовые данные с нужными правилами переноса инвентаря, ресурсов,
слепоты, стана и других воздействий. `PieceCreationContext(square, source)` содержит
исходную клетку нового состояния и источник призыва/превращения; `source` может
отсутствовать при начальном назначении. Фабрика вызывает политику, сохраняет
запрошенную идентичность, форму, сторону и размещение, затем проверяет результат.

Обычные обновления `PieceState` не вызывают инициализацию повторно и не меняют
исходный цвет по текущей клетке. Общие инварианты (ID, неотрицательные значения,
размещение, поддерживаемая фигура, три слота) проверяет сама модель.
Специфическое состояние проверяется через `HeroRegistry.validateState` /
`validateStates` при создании, на выходе предпросмотра, перед публикацией и загрузкой.
Промежуточный объект с непроверенными полями нельзя публиковать в партии.
Нарушение политики — ошибка состояния, а не новая причина игрового отказа.

При восстановлении драфта `validateOrigin` получает исходную клетку из сохранённого
пика. Связи с другими фигурами и историей — проглоченный союзник, источник иллюзии,
ячейки болота и сроки эффектов — проверяют соответствующие механики и проверка
согласованности снимка. Политика не заменяет эти проверки.

### Настройки партии

`HeroRules.defaults()` создаёт неизменяемый контейнер стандартных параметров всех
описаний из `HeroDefinitions.all()`. Настройки переопределяются типизированно:

```java
HeroRules rules = HeroRules.defaults()
        .with(PudgeDefinition.INSTANCE, new PudgeRules(4, 3, true, false));
PudgeRules parameters = rules.get(PudgeDefinition.INSTANCE);
```

`with` возвращает новый контейнер. Тип параметров должен соответствовать описанию;
подмена описания с тем же ID отклоняется. Не добавлять в общий `HeroRules` отдельные
поля, геттеры или конструкторы для нового героя. `GoldRules` задаёт экономику партии
отдельно от параметров героев через `withGold`.

### Кодек параметров

`<Name>RulesCodec implements HeroRulesCodec<<Name>Rules>` явно реализует:

- `section()` — стабильное имя XML-секции параметров;
- `sinceVersion()` — версию формата, начиная с которой эта секция обязательна;
- `encode(Rules)` — атрибуты секции как `Map<String, String>`;
- `decode(HeroRuleAttributes)` — создание валидированного объекта правил.

Использовать `HeroRuleAttributes.integer`, `bool` и `text` для чтения атрибутов.
Не использовать reflection, имена Java-классов из файла или общий `switch` по герою.
Кодек подключается через описание; `HeroRulesXml` обходит зарегистрированные кодеки,
проверяет наличие и версию секций и передаёт параметры в типизированный контейнер.
До `sinceVersion()` применяются стандартные параметры описания.

Имена секций, атрибуты и значения существующих параметров сохранять.
`beforeSection()` определяет размещение секции в XML; стандартное место — перед
`castling`. При переносе старой схемы сохранить её прежнее расположение.


Образец конструктора из `PudgeHero`:

```java
public PudgeHero(PudgeRules rules) {
    super(PudgeDefinition.INSTANCE, PudgeAbility.getAbilities(), PudgeAbility.SWALLOW,
            Objects.requireNonNull(rules, "rules").ultimateCaptures());
    this.rules = rules;
}
```

Конфигурация базы: описание героя, неизменяемый список способностей, активная ульта
и порог заряда. Тип героя берётся из описания.
`ultimateAbility == null` означает отсутствие активной ульты; положительный порог
при этом может ограничивать заряд пассивной способности.
Нулевой порог делает ульту бесплатной и отключает общее накопление заряда.

## 5. Контракты Hero и AbstractHero

| Метод | Что делать в наследнике AbstractHero |
| --- | --- |
| `definition()` / `type()` / `abilities()` | Предоставляет база, методы final |
| `availability(PieceState, Abilities)` | Final-вход обычного применения |
| `availability(PieceState, Abilities, AbilityUse)` | Общий final-шаблон обоих каналов; не переопределять |
| `availabilitySpecific(PieceState, Abilities, AbilityUse)` | Особые требования к настоящему исполнителю; не дублировать проверки стоимости |
| `preview(HeroActionContext, AbilityRequest)` | Основной final-шаблон; не переопределять |
| `previewAvailable(HeroActionContext, PieceState, PieceState, AbilityRequest)` | Единственный обязательный protected-метод: геометрия, специфические проверки и эффект |
| `abilityEventDetails(HeroActionContext, HeroActionContext, PieceState, PieceState, AbilityRequest)` | ID цели, итоговая клетка и метаданные полученной копии для события |
| `afterCapture(PieceState)` | Общее начисление заряда; переопределять только при особых правилах |
| `supports(Class<? extends Figure>)` | По умолчанию делегирует `definition().supports` |
| `targeting(Abilities)` | По умолчанию берёт политику из enum способности |
| `requests(HeroActionContext, PieceState, Abilities, boolean)` | Полные запросы-кандидаты по схеме выбора; переопределять для своей геометрии |
| `onCaptured(HeroActionContext, PieceState, long, Position)` | Необязательная собственная пассивная реакция героя; по умолчанию пустой эффект |
| `abilityMessage(HeroActionContext, HeroActionContext, PieceState, PieceState, AbilityRequest)` | Необязательная подпись события; при миграции сохранить прежний текст |

Доступность в базе проверяет по порядку: отсутствие способности, горшок исполнителя,
активность фигуры на доске, соответствие героя и способности, кулдаун обычной
способности, `availabilitySpecific`, достаточный заряд ульты.
Один кулдаун фигуры применяется к способностям, не являющимся `ultimateAbility`.
Проверка кулдауна обычной способности не распространяется на ульту.

`preview(context, request)` отклоняет отсутствующую способность, проверяет клетку
исполнителя и находит исполнителя через `context.pieceAt(request.actor())`.
Затем выполняет `availability`, общую проверку `HeroTargeting` и вызывает
`previewAvailable(context, actor, target, request)` с целью из того же контекста.
`target` может быть `null` для пустой клетки или способности без цели.
Полный `request` сохраняет `ability`, `target`, `destination` и `borrowed`.
Не восстанавливать эти параметры из имени способности или состояния стратегии.

В методе героя проверять необходимые цели, геометрию, наличие и границы `destination`
в том порядке, который задают правила способности. Общая проверка формы отклоняет
лишнюю вторую клетку; она не переносит проверку обязательной клетки назначения
перед специфической геометрией. При миграции сохранять приоритет причин отказа.
Права игрока, состояния запрета действия, бюджет хода, безопасность короля,
обработчики механик и возможность завершить ход проверяет ядро.
Прямой вызов стратегии не заменяет эти проверки партии.

### Запросы-кандидаты и подсветка

`requests(context, actor, ability, borrowed)` возвращает неизменяемый список полных
`AbilityRequest`. Каждый кандидат содержит исполнителя, способность, цель,
необходимую клетку назначения и исходный канал `borrowed`.
По умолчанию база интерфейса перечисляет клетки по схеме: один запрос без цели,
все клетки для одной цели или пары клеток для двух этапов. Герой может сузить
генерацию по своей геометрии, не исключая ни одного допустимого применения.
Не создавать отдельную реализацию законности действия для подсветки.

`Game.getAbilityTargets` выбирает первые клетки из успешных полных запросов.
`Game.getAbilityDestinations(actor, ability, target, borrowed)` выбирает вторые
клетки для зафиксированной первой. Оба метода используют тот же предпросмотр,
механики и проверку продолжения хода, что исполнение. Запрос, переданный напрямую,
также проходит проверки; наличие в списке кандидатов не заменяет валидацию.
UI определяет этап по `HeroTargeting` и передаёт выбранные клетки в один запрос.

### Канал применения и стоимость

`AbilityUse(owner, channel)` отделяет владельца правил от исполнителя.
`Channel.NATIVE` — собственная способность, `BORROWED` — применение копии.
Владелец копии определяется через `HeroRegistry.ownerOf` реестра конкретной партии.
Стратегия всегда получает настоящий `PieceState`: не подменять `hero`, шахматную
форму, ресурсы, стартовый цвет или статусы для выполнения чужой способности.
`request.borrowed()` сохраняет канал в полном запросе и операциях механик.

Обычное применение и копия используют один `previewAvailable` и одни правила
геометрии. `availabilitySpecific(actor, ability, use)` проверяет ограничения эффекта
по настоящему исполнителю: например, занят ли слот проглоченного союзника или
доступна ли следующая форма эволюции. Пассивные способности владельца правил
не передаются исполнителю копии.

Кулдаун и расход заряда активации указывать отдельно от эффекта через `AbilityCost`:

```java
return HeroEffect.success(updates).withCost(AbilityCost.cooldown(rules.hookCooldown()));
// Для ульты: .withCost(AbilityCost.ultimate(ultimateCaptures())).
```

`AbilityCost.cooldown(turns)` устанавливает кулдаун, `ultimate(charge)` списывает
заряд. Конструктор `new AbilityCost(cooldown, charge)` задаёт оба изменения;
`cooldown == null` сохраняет прежнее значение. Стоимость по умолчанию — `NONE`.
Нулевой кулдаун означает установку нуля, а не отсутствие изменения.
Не записывать эти расходы вручную в обновления `PieceState` и не обнулять `Rules`.
Для расчёта доступны protected final `ultimateAbility()` и `ultimateCaptures()`.

База проверяет собственные ресурсы при `NATIVE`; при `BORROWED` пропускает их
проверку и расход. Специфические ограничения эффекта сохраняются для обоих каналов.
После успешной геометрии база применяет стоимость ровно один раз к предложенному
состоянию исполнителя и очищает `cost`. Это происходит до операций механик,
взятий и их наград. Перемещение, превращение и изменение особого состояния входят
в эффект; награды за последующие взятия рассчитываются для настоящего исполнителя.
Обработчик новой механики не списывает повторно стоимость активации.

При отказе возвращать `HeroEffect.rejected(...)` без обновлений, взятий, операций
и стоимости. Отказ не расходует копию. Готовность, получение, успешный расход и
замену слота копии обслуживает механика Ginseng; стратегия эффекта не управляет им.

## 6. Контекст, эффекты и реакции

`HeroActionContext` содержит `field`, неизменяемую карту `pieces`, `currentTurn`
и неизменяемый контейнер `MechanicStates mechanics`. Состояние своей механики
получать через `context.state(MyMechanic.KEY)` с типизированным `MechanicKey<S>`.
Новая механика не добавляет поле в контекст или `GameSnapshot`.
Для поиска фигур использовать `pieceAt` и `pieceById`.

Контекст не даёт права изменять `Field`: занятость читать из карты фигур,
`field.createFigure` использовать для отделённого описания шахматной фигуры.
Конструктор из трёх аргументов предоставляет стандартные состояния ключей.
В тестах, зависящих от механики, передавать её состояние через контейнер.
Именованные геттеры `terrain`, `faun`, `spells`, `economy`, `summons`, `clown`,
`mines`, `lightning` читают тот же контейнер и не образуют второго состояния.

`HeroEffect` содержит `result`, `Map<Long, PieceState> updates`,
`List<Capture> captures`, `List<MechanicOperation> operations`, `AbilityCost cost`.
Коллекции неизменяемы. При обновлении фигуры сохранять остальные свойства.
Отклонённый эффект не содержит изменений. `withOperations(...)` возвращает новый
эффект с добавленными операциями; сама операция — неизменяемые данные.

Герой предлагает эффект. Ядро применяет его в отдельной `MechanicSession`,
разрешает цепочки, проверяет результат и готовит журнал. `Game` публикует
фигуры, состояния, ресурсы, взятия, бюджет и события только после успеха.
Предпросмотр и отказ не расходуют ID, случайность или ресурсы живой партии.
Бюджет хода, безопасность короля и публикация остаются ответственностью ядра.

### Модуль механики

Для самостоятельной механики реализовать `MechanicDefinition<S>` и объявить
единственный экземпляр модуля рядом с его состоянием. Модуль и обработчики
не хранят изменяемых данных партии.

| Часть модуля | Обязательство |
| --- | --- |
| `key()` | Единственный `MechanicKey<S>` со стабильным ID, `Class<S>` и неизменяемым начальным состоянием |
| `dependencies()` | Необходимые модули; граф без циклов |
| `handlers()` | Типизированные `MechanicHandler<O>` для классов операций `O implements MechanicOperation` |
| `steps()` | Реакции жизненного цикла через `MechanicStep` |
| `captureReactions()` | Реакции собственного состояния механики на гибель через `MechanicCaptureReaction` |
| `events()` | Канонические `MechanicEventType<P>`: стабильный ID, тип данных, явные кодеки и политика ссылок |
| `codec()` | Явное чтение/запись собственного состояния через `MechanicStateCodec<S>` |
| `restore(snapshot)` | Восстановление состояния, если оно полностью выводится из истории; стандартно начальное состояние |
| `validate(snapshot)` | Согласованность состояния, фигур, ресурсов и истории механики |
| `allowsExtraMove(context, actor)` | Разрешение дополнительного перемещения, если оно предусмотрено правилами механики |

Один и тот же экземпляр модуля может использоваться несколькими героями.
Совпадение ID разных модулей, типов обработчиков операций, ID шагов или событий
отклоняется при создании реестра. Не использовать один ID для разных ключей.

Обработчик получает `MechanicSession` и данные операции. Состояние читать и
записывать типизированно через `state(KEY)` / `state(KEY, next)`; фигуры — через
`pieces`, `update`; взятие с зарядом и ответными реакциями — через
`capture(actorId, victimId)`. Возвращать `MoveResult`. Не изменять `Game`,
`Player`, часы или поле исходного контекста. Рабочую сессию не сохранять в модуле.
`local(KEY, value)` предназначен для временных данных одного предпросмотра,
которые не должны попадать в снимок партии.

Фазу обработчика/шага задавать через `MechanicPhase`. ID шагов уникальны;
`before` / `after` ссылаются на существующие шаги той же фазы. Циклы, неизвестные
ссылки и зависимости между разными фазами запрещены. При переносе сохранять
прежнюю последовательность, включая реакции внутри входа на клетку и призыва.

| Фазы | Назначение |
| --- | --- |
| `SETUP` | Проверка начального назначения и подготовка состояний механик |
| `MOVE_START`, `MOVE_PATH`, `MOVE_ATTACKER`, `MOVE_TARGET` | Проверки и взаимодействия обычного перемещения; данные в `movement()` |
| `ABILITY_GUARD`, `ABILITY_PREPARE` | Проверки контекста и выполнение операций способности; запрос в `request()` |
| `ENTRY` | Входы на клетки и цепочки; повторяется до стабилизации с ограничением числа итераций |
| `SETTLED`, `AFTER_SAFETY`, `AFTER_ACTION` | Очистка, результаты взятий и завершающие операции действия |
| `AFTER_MOVE` | Учёт выполненного перемещения |
| `CAN_END` | Изолированная проверка возможности закончить ход |
| `END_TURN` | Превращения, истечение состояний и прочие изменения конца хода |
| `HISTORY`, `END_HISTORY` | Только подготовка записей; игровые состояния изменять запрещено |

Поле в `session.context()` служит исходной геометрией и фабрикой; актуальная
занятость находится в `session.pieces()`. Не предполагать наличие `request()`
в фазах обычного перемещения, завершения хода и формирования истории.

Для сохраняемого состояния предоставить кодек либо полное восстановление из
истории через `restore`. Если кодека нет, запись проверяет равенство состояния
результату восстановления. Зависимые состояния восстанавливаются после своих
зависимостей. Поля собственного формата, их допустимость и версию описывает
локальный кодек; не использовать reflection или имена Java-классов из файла.
`legacyWireState()` не переопределять для новых механик.

### События и реакции

Длительные последствия способности размещать в модуле механики и привязывать
к ID настоящего исполнителя. Они продолжают работать после расходования копии.
Состояние хранить в `PieceState` либо типизированном контейнере и сохранять
общим путём; не связывать срок эффекта с наличием способности в слоте копии.

`captureReactions()` возвращает неизменяемые `MechanicCaptureReaction` с ID,
зависимостями `before` / `after` и функцией `DeathContext -> HeroEffect`.
`DeathContext` содержит жертву до удаления, ID убийцы, клетку гибели и контекст
подготовленных фигур/механик. Реакция определяет применимость по этому состоянию;
при отсутствии собственного эффекта возвращает `HeroEffect.empty()`.

Сначала выполняется собственная `Hero.onCaptured`, затем реакции модулей в
порядке зависимостей. Неизвестные ссылки, повторные ID и циклы запрещены.
Каждая реакция видит результат предыдущей. Её операции выполняются синхронно,
а последующие гибели обрабатываются общей очередью с сохранением порядка.
Пример долгого последствия: [SwallowMechanic](../composeApp/src/jvmMain/java/game/heroes/pudge/SwallowMechanic.java).


Специальное событие имеет категорию `MECHANIC_EFFECT`, `MechanicEvent<P>` с
типизированными неизменяемыми данными и зарегистрированный `MechanicEventType<P>`.
Обработчик предлагает его через `session.propose(new MechanicEventDraft(...))`.
Номер записи назначает общий путь; не вычислять его в стратегии.
Политика `MechanicEventPolicy` задаёт привязку к активному ходу и обязательность
исполнителя, цели и координат. Смысл данных проверяет модуль.

Общее взятие новой механикой записывается как `GameEvent.Kind.CAPTURE`;
детали воздействия описывает её типизированное событие. Не добавлять название
механики в `GameEvent.Kind` или `Capture.Cause`: использовать общий
`Capture.Cause.MECHANIC` либо `session.capture`.

`onCaptured` получает жертву до удаления, ID убийцы и клетку гибели.
`context.pieces()` уже содержит подготовленные состояния после удаления,
контейнер — актуальные состояния механик. Возвращать один `HeroEffect`,
в том числе с операциями. Операции реакции выполняются в точке этой гибели
до следующей гибели в очереди. Не рекурсировать самостоятельно:
очередь ведёт `CaptureReactions`. Выжившему исполнителю ответного взятия врага
заряд начисляет общий механизм.

Подробности API: [MECHANICS.md](../docs/MECHANICS.md).

## 7. HeroRegistry

Добавить стабильную константу в `HeroType` и описание `<Name>Definition.INSTANCE`
в единственный список регистрации `HeroDefinitions.all()`.
Не изменять `HeroRegistry.fromRules` для подключения отдельного героя.

`HeroRegistry.fromRules(rules)` обходит `rules.definitions()`, создаёт стратегии
через их фабрики и индексирует способности. Тип должен разрешаться в `<Name>Hero`
с соответствующим описанием. Не регистрировать для него универсальный адаптер.

Реестр неизменяем; ручной `register(hero)` возвращает новый экземпляр, который
нужно сохранить. Повторная регистрация типа, пустые и повторяющиеся ID способностей
отклоняются. В конфигурации также отклоняются повторные типы описаний и имена секций.

`Game` создаёт реестр для правил партии один раз и передаёт его в подготовленные
контексты. `get(type)` возвращает стратегию; `abilityById(id)` — каноническую константу;
`ownerOf(ability)` — стратегию-владельца именно зарегистрированного экземпляра.
`findAbility(id)` возвращает null для неизвестного ID.

`HeroDefinitions.get(type)` предоставляет описание без создания стратегии.
`HeroRegistry.standard()` — реестр на стандартных правилах из той же фабрики регистрации.
Не использовать его вместо игрового реестра для расчёта баланса.
Индексы способностей строятся из `Hero.abilities()`, отдельного списка enum нет.
`registry.mechanics()` предоставляет собранный реестр модулей из зависимостей описаний.
Сохранения записывают `id()`, а чтение использует реестр.

### Событие успешного применения

Все способности используют `GameEvent.Kind.ABILITY_USED`.
`GameEvent.ability()` хранит канонический экземпляр `Abilities`, `abilityId()` возвращает
его стабильный `id()`. Для проверки конкретной способности использовать
`event.isAbility(<Name>Ability.CONSTANT)`, для категории — `event.kind()`.
Не добавлять имя способности в `GameEvent.Kind` и не вызывать `Kind.valueOf(ability.id())`.

Ядро создаёт запись через `GameEvent.abilityUsed(...)` и заполняет исполнителя,
цель, координаты и текст. `copiedAbility` содержит полученную копию, `borrowed`
отмечает применение сохранённой копии. Стратегия не добавляет запись в журнал сама.
Категория применения требует `ability`; перемещения, границы хода, взятия и реакции
не должны содержать `ability`, `copiedAbility` или `borrowed`.

В enum способности задать `eventTarget()` по смыслу `targetId`:

- `AbilityEventTarget.REQUIRED` — запись содержит ID фигуры-цели; это значение по умолчанию.
- `AbilityEventTarget.OPTIONAL` — способность применима к занятой или пустой клетке.
- `AbilityEventTarget.NONE` — запись не связывается с фигурой-целью.

Например, хук имеет `REQUIRED`, болото — `OPTIONAL`, телепорт — `NONE`.
`HeroTargeting` проверяет выбор клетки, а `eventTarget` — форму данных истории.
Эти политики задавать согласованно с механикой; наличие клетки не обязательно означает
наличие фигуры-цели. Ошибку применения не записывать как успешное событие.

`GameEventXml` сериализует общую категорию и отдельный ID. Новые ID не требуют
изменения кодека; чтение разрешает ID через реестр. Память применений и копий
восстанавливается из поля `ability`, независимо от имени категории.
Для нестандартного набора зарегистрированных описаний передать его стандартные
правила в `GameSaveFile.decode(bytes, defaults)`; обычная загрузка использует
описания из `HeroDefinitions`. Новые данные механик используют XML 16;
подключение локального кодека не требует новой ветки в `GameSaveFile`.

### Отображение и общая панель

Для каждого видимого героя создать локальный `<Name>Presentation` в
`org.chess.heroes.<имя>` и зарегистрировать в `HeroPresentations.all`.
Использовать `HeroPresentation` / `BaseHeroPresentation`: подпись, описание,
значок, текст состояния и необязательные виджеты или изображения.
Не помещать Compose, ресурсы и размеры UI в `HeroDefinition`, `Hero` или `Rules`.

`HeroPresentationRegistry` проверяет комплектность при подключении UI;
движок и его тесты не зависят от представлений. Изображение необязательно:
текстовый значок и имя обеспечивают основное отображение.
`HeroViewContext` содержит снимок, отображаемую фигуру, выбор способности и
неизменяемый реестр партии. Параметры баланса получать типизированно через
`context.snapshot.heroRules().get(<Name>Definition.INSTANCE)`.

Общая `HeroPanel` строит кнопки по `Hero.abilities()`. Представление может задавать
`label(ability)`, `Details`, `AfterActions` и `Extra`, но не копирует перечень кнопок
и обработчик применения. Локальный виджет использует `HeroPanelControls.AbilityButton`
и `Rejection`; копия передаётся с `borrowed = true`.
В представлении не рассчитывать законность, геометрию, стоимость и игровые эффекты
и не вызывать `Game.useAbility` напрямую. Все действия проходят общий выбор
`HeroTargeting`, подсветку `Game` и полный `AbilityRequest`.
Не добавлять имя нового героя или способности в `ChessBoard` и `DraftScreen`.

Ресурсы, динамический значок и особые сведения размещать локально через
`boardBadge`, `draftSummary`, `Portrait`, `CellDecoration` и виджеты представления.
Правила драфта и игровые метаданные не должны зависеть от UI-реестра.
[Полный контракт отображения](../docs/HERO_PRESENTATION.md).

## 8. Порядок работы и критерии готовности

1. Зафиксировать механику: базовая шахматная фигура, способности, цели, стоимость,
   пассивные реакции и взаимодействия. Для миграции взять прежнее поведение за эталон.
2. Определить реализацию механики через контекст, запросы, эффекты и точки
   расширения этого контракта. Не изменять общие API при реализации отдельного героя.
3. Создать enum, Rules, кодек, описание и стратегию; подключить необходимые модули. Список способностей брать через `getAbilities()`.
4. Добавить ID в `HeroType`, описание с `DraftProfile` в `HeroDefinitions`;
   создать локальный `HeroPresentation` и зарегистрировать в `HeroPresentations.all`.
   Сохранить совместимость истории и форматов. Не добавлять ветки героя в ядро.
5. Проверить поведение и интеграцию, затем обновить документацию героя.

Проверки выбирать по механике: допустимые и неверные цели, границы и препятствия,
нужные статусы, стоимость только при успехе, заряд и кулдаун, начальное назначение
совместимой фигуре, отсутствие мутаций при повторных предпросмотрах.
Для взятий проверить реакции и награды; для копируемых способностей — Ginseng;
для сохраняемого состояния — запись, загрузку и продолжение партии.
Регистрация должна сохранять уникальность ID и каноническую идентичность способностей.
Новую способность проверить через `Game`: успешное применение, категорию и ID события,
сохранение, загрузку и продолжение партии. Для каждой активной способности проверить получение и расход копии, настоящий
тип и статусы исполнителя, сохранение его собственных ресурсов, ограничения
эффекта и продолжение после восстановления журнала. Длительные последствия
проверить после расходования копии и загрузки, включая применимые реакции.
Для новой механики проверить операции и реакции, отказ без публикации,
типизированные события, кодек/восстановление и продолжение партии после загрузки.
Подсветка целей и выполнение запроса должны согласовываться. Проверить участие
в каталоге, начальные клетки, неизменность сохранённого состава при расширении
реестра и выполнение новых способностей через общую панель UI.

Для политики проверить исходные поля, допустимые превращения, специальные статусы
и пределы по нестандартным параметрам партии. Проверить, что некорректный результат
не публикуется и не загружается; обычные обновления сохраняют исходные данные.

Полный прогон из корня: `bash gradlew :composeApp:jvmTest`.
Только юнит-теста `preview` недостаточно для нового героя: проверить вызов через
`Game`, запись события и необходимые взаимодействия.
Не менять правила игры ради соответствия каркасу.
