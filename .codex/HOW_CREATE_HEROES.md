# Как создавать и переносить героев

Обязательный контракт создания и переноса героя. Общие правила кода:
[AGENTS.md](AGENTS.md).

## 1. Границы ответственности

Подключение героя состоит из реализации по этому контракту, регистрации,
добавления отображения и ресурсов. Поведение героя не должно требовать веток
по его типу или способностям в `Game`, `ActionEngine` и общих обработчиках.
При переносе существующего героя сохранять его игровые правила и наблюдаемые результаты.

Агент, реализующий героя, использует общий контракт и не меняет его в рамках
переноса одного героя. Изменения общих API проектируются отдельной задачей.
Пример реализации: [PudgeHero](../composeApp/src/jvmMain/java/game/heroes/pudge/PudgeHero.java).

## 2. Файлы и ответственность

```text
composeApp/src/jvmMain/java/game/heroes/<имя>/
  <Name>Ability.java       enum: идентичность, подпись, политика целей, список
  <Name>Rules.java         неизменяемые параметры баланса
  <Name>Hero.java          final class extends AbstractHero: правила и эффекты
  <Name>Definition.java    HeroDefinition<Rules>: описание и фабрика стратегии
  <Name>RulesCodec.java    явное чтение и запись параметров героя
composeApp/src/jvmTest/java/game/heroes/<имя>/
  <Name>HeroTest.java      проверки игрового поведения
```

Дополнительные типы в пакете нужны только для самостоятельных понятий механики.
Эффекты реализовать в `<Name>Hero`. Не создавать статический `<Name>Abilities`
с отдельной реализацией поведения или диспетчеризацией.

`Hero` — переиспользуемая стратегия. Две фигуры одного героя могут пользоваться
одним объектом поведения и иметь совершенно разные состояния.
`PieceState` хранит ID, текущую шахматную форму, героя, позицию, статусы и ресурсы фигуры.
Не хранить эти значения в полях стратегии.

Герой назначается совместимой шахматной фигуре в начале игры; это не наследование
`Hero` от `Rook`, `Bishop` и т. п. Допустимые начальные фигуры задаются в
`HeroDefinition.supportedBodies()`. `Hero.supports` использует это описание.
`HeroType` хранит только идентичность героя (`PUDGE`, `ZEUS`, `GINSENG`),
без суффикса шахматной фигуры, отображаемого названия и правил совместимости.
Проверка назначения проходит через реестр.
Превращение фигуры и копирование способности имеют собственные правила:
не назначать героя заново при каждом действии по текущему классу фигуры.

## 3. Enum способностей

Каждый герой объявляет собственный `enum <Name>Ability implements Abilities`.
Интерфейс требует `id()` и `getDisplayName()`; `targeting()` имеет реализацию
по умолчанию. В enum явно задать политику каждой способности.
`eventTarget()` задаёт наличие идентификатора цели в записи успешного применения.

Пример устройства на существующем Пудже:

```java
public enum PudgeAbility implements Abilities {
    HOOK("HOOK", "Хук", HeroTargeting.square(
            HeroTargeting.Permission.ILLUSION, HeroTargeting.Permission.POTTED)),
    SWALLOW("SWALLOW", "Проглотить", HeroTargeting.square());

    private static final List<Abilities> ABILITIES = Abilities.getAbilities(values());

    private final String id;
    private final String displayName;
    private final HeroTargeting targeting;

    PudgeAbility(String id, String displayName, HeroTargeting targeting) {
        this.id = id;
        this.displayName = displayName;
        this.targeting = targeting;
    }

    public static List<Abilities> getAbilities() { return ABILITIES; }
    @Override public String id() { return id; }
    @Override public String getDisplayName() { return displayName; }
    @Override public HeroTargeting targeting() { return targeting; }
}
```

В файле нужны импорты `game.heroes.Abilities`, `game.heroes.HeroTargeting`, `java.util.List`.
Список создаётся один раз, неизменяем и сохраняет порядок объявления.
Новая константа автоматически входит в список: вручную перечислять её в герое не нужно.
Статический `getAbilities()` — договорённость для enum. Java не позволяет требовать
переопределения статического метода интерфейса; `Abilities.getAbilities(values())`
является общей фабрикой списка.

ID — явный стабильный ключ сохранений, уникальный среди всех зарегистрированных
способностей. Не выводить его из `ordinal()`, `name()` или отображаемого текста.
Прежние ID не переименовывать.

### Политика целей

`HeroTargeting.square(...)` требует клетку; `untargeted()` не требует цели.
Разрешения: `SELF`, `KING`, `INVISIBLE`, `POTTED`, `BOXED`, `ILLUSION`, `DESTINATION`.
Без соответствующего разрешения общая проверка отклоняет такой запрос.
`DESTINATION` разрешает дополнительную клетку назначения, но само по себе
не реализует её выбор и обработку.

Политика не задаёт дальность, препятствия, дружественность цели и требование
занятой/пустой клетки. Всё это проверяет конкретный герой.
`HeroTargeting.validate` может успешно проверить пустую клетку: это не означает,
что любая способность может применяться туда.
Порядок общих причин отказа сохранять при миграции.

## 4. Описание, Rules и конструктор героя

`<Name>Rules` — неизменяемый record или класс с валидацией параметров.
Числа баланса хранить здесь; стратегия получает правила через конструктор.
Не брать `prototype()` внутри каждого игрового вызова: использовать правила партии.

### HeroDefinition

В `<Name>Definition` объявить одну `public static final HeroDefinition<<Name>Rules> INSTANCE`.
Описание содержит `HeroType`, отображаемое название, неизменяемый набор совместимых
начальных шахматных фигур, `Class<Rules>`, стандартные параметры, кодек и фабрику.
Чтение описания не создаёт стратегию и не зависит от состояния партии.

```java
public static final HeroDefinition<PudgeRules> INSTANCE = new HeroDefinition<>(
        HeroType.PUDGE, "Пудж-Ладья", Set.of(Rook.class),
        PudgeRules.class, PudgeRules.prototype(), new PudgeRulesCodec(), PudgeHero::new);
```

Фабрика получает параметры своего героя и создаёт его `<Name>Hero`.
`hero.definition()` должен возвращать именно это описание. Передать `INSTANCE`
в конструктор `AbstractHero`, чтобы база предоставляла `definition()` и `type()`.

### Настройки партии

`HeroRules.defaults()` создаёт неизменяемый контейнер стандартных параметров всех
описаний из `HeroDefinitions.all()`. Настройки переопределяются типизированно:

```java
HeroRules rules = HeroRules.defaults()
        .with(PudgeDefinition.INSTANCE, new PudgeRules(4, 3, true, false));
PudgeRules parameters = rules.get(PudgeDefinition.INSTANCE);
```

`with` возвращает новый контейнер. Тип параметров должен соответствовать описанию;
подмена описания с тем же ID отклоняется. Не добавлять в общий `HeroRules` отдельные
поля, геттеры или конструкторы для нового героя. `GoldRules` задаёт экономику партии
отдельно от параметров героев через `withGold`.

### Кодек параметров

`<Name>RulesCodec implements HeroRulesCodec<<Name>Rules>` явно реализует:

- `section()` — стабильное имя XML-секции параметров;
- `sinceVersion()` — версию формата, начиная с которой эта секция обязательна;
- `encode(Rules)` — атрибуты секции как `Map<String, String>`;
- `decode(HeroRuleAttributes)` — создание валидированного объекта правил.

Использовать `HeroRuleAttributes.integer`, `bool` и `text` для чтения атрибутов.
Не использовать reflection, имена Java-классов из файла или общий `switch` по герою.
Кодек подключается через описание; `HeroRulesXml` обходит зарегистрированные кодеки,
проверяет наличие и версию секций и передаёт параметры в типизированный контейнер.
До `sinceVersion()` применяются стандартные параметры описания.

Имена секций, атрибуты и значения существующих параметров сохранять.
`beforeSection()` определяет размещение секции в XML; стандартное место — перед
`castling`. При переносе старой схемы сохранить её прежнее расположение.


Образец конструктора из `PudgeHero`:

```java
public PudgeHero(PudgeRules rules) {
    super(PudgeDefinition.INSTANCE, PudgeAbility.getAbilities(), PudgeAbility.SWALLOW,
            Objects.requireNonNull(rules, "rules").ultimateCaptures());
    this.rules = rules;
}
```

Конфигурация базы: описание героя, неизменяемый список способностей, активная ульта
и порог заряда. Тип героя берётся из описания.
`ultimateAbility == null` означает отсутствие активной ульты; положительный порог
при этом может ограничивать заряд пассивной способности.
Нулевой порог делает ульту бесплатной и отключает общее накопление заряда.

## 5. Контракты Hero и AbstractHero

| Метод | Что делать в наследнике AbstractHero |
| --- | --- |
| `definition()` / `type()` / `abilities()` | Предоставляет база, методы final |
| `availability(PieceState, Abilities)` | Общий final-шаблон; не переопределять |
| `availabilitySpecific(PieceState, Abilities)` | Переопределять при особых требованиях к исполнителю |
| `preview(HeroActionContext, PieceState, PieceState, Position, Abilities)` | Общий final-шаблон; не переопределять |
| `previewAvailable(HeroActionContext, PieceState, PieceState, Position, Abilities)` | Обязательно реализовать геометрию, специфические проверки и эффект |
| `afterCapture(PieceState)` | Общее начисление заряда; переопределять только при особых правилах |
| `supports(Class<? extends Figure>)` | По умолчанию делегирует `definition().supports` |
| `targeting(Abilities)` | По умолчанию берёт политику из enum способности |
| `requests(HeroActionContext, PieceState, Abilities, boolean)` | По умолчанию все клетки или один запрос без цели; расширять для особого выбора |
| `onCaptured(HeroActionContext, PieceState, long, Position)` | Необязательная реакция на гибель; по умолчанию пустой эффект |
| `abilityMessage(HeroActionContext, HeroActionContext, PieceState, PieceState, AbilityRequest)` | Необязательная подпись события; при миграции сохранить прежний текст |

Доступность в базе проверяет по порядку: отсутствие способности, горшок исполнителя,
активность фигуры на доске, соответствие героя и способности, кулдаун обычной
способности, `availabilitySpecific`, достаточный заряд ульты.
Один кулдаун фигуры применяется к способностям, не являющимся `ultimateAbility`.
Проверка кулдауна обычной способности не распространяется на ульту.

`preview` проверяет доступность и вызывает `previewAvailable` только при успехе.
Общие проверки `HeroTargeting` выполняет игровой путь в `ActionEngine` перед
предпросмотром; сам final-метод `AbstractHero.preview` их не запускает.
Не предполагать, что отдельный прямой вызов `preview` прошёл все проверки ядра.

При успехе наследник включает стоимость в изменения исполнителя:
кулдаун обычной способности и/или расход заряда ульты. База сама их не списывает.
Для расчёта доступны protected final `ultimateAbility()` и `ultimateCaptures()`.
При отказе возвращать `HeroEffect.rejected(...)` без обновлений и взятий.

## 6. Контекст, эффекты и реакции

`HeroActionContext` передаёт `field`, неизменяемую карту `pieces`, `currentTurn`,
`terrain`, `faun`, `spells`, `economy`. Использовать `pieceAt` и `pieceById`
для поиска фигур. Контекст не даёт права изменять `Field`: record не превращает
вложенные изменяемые объекты в глубоко неизменяемые.
Конструктор из трёх аргументов даёт пустые дополнительные состояния;
для способностей, зависящих от них, тесты должны задавать полный контекст.

`HeroEffect` содержит только `result`, `Map<Long, PieceState> updates` и
`List<Capture> captures`. Возвращать новые состояния, сохраняя остальные свойства.
Гибель фигуры и описание соответствующего взятия должны согласовываться.
Не начислять награды и не изменять историю самостоятельно.

Цепочка: `Game` → `ActionEngine` → реестр → проверки и `Hero.preview` →
`HeroEffect` → подготовка и проверка ядром → публикация успешного состояния в `Game`.
Бюджет хода, безопасность короля и публикация результата остаются ответственностью ядра.

`onCaptured` получает жертву до удаления, ID убийцы и клетку гибели;
`context.pieces()` уже содержит подготовленные состояния после удаления.
Поле в реакции может отражать более раннюю доску: занятость читать из карты фигур,
`field.createFigure` использовать для отделённого описания взятой шахматной фигуры.
Не рекурсировать по цепочке гибелей самостоятельно — очередь ведёт `CaptureReactions`.
Выжившему исполнителю ответного взятия врага заряд начисляет общий механизм.

## 7. HeroRegistry

Добавить стабильную константу в `HeroType` и описание `<Name>Definition.INSTANCE`
в единственный список регистрации `HeroDefinitions.all()`.
Не изменять `HeroRegistry.fromRules` для подключения отдельного героя.

`HeroRegistry.fromRules(rules)` обходит `rules.definitions()`, создаёт стратегии
через их фабрики и индексирует способности. Тип должен разрешаться в `<Name>Hero`
с соответствующим описанием. Не регистрировать для него универсальный адаптер.

Реестр неизменяем; ручной `register(hero)` возвращает новый экземпляр, который
нужно сохранить. Повторная регистрация типа, пустые и повторяющиеся ID способностей
отклоняются. В конфигурации также отклоняются повторные типы описаний и имена секций.

`Game` создаёт реестр для правил партии один раз и передаёт его в подготовленные
контексты. `get(type)` возвращает стратегию; `abilityById(id)` — каноническую константу;
`ownerOf(ability)` — стратегию-владельца именно зарегистрированного экземпляра.
`findAbility(id)` возвращает null для неизвестного ID.

`HeroDefinitions.get(type)` предоставляет описание без создания стратегии.
`HeroRegistry.standard()` — реестр на стандартных правилах из той же фабрики регистрации.
Не использовать его вместо игрового реестра для расчёта баланса.
Индексы способностей строятся из `Hero.abilities()`, отдельного списка enum нет.
Сохранения записывают `id()`, а чтение использует реестр.

### Событие успешного применения

Все способности используют `GameEvent.Kind.ABILITY_USED`.
`GameEvent.ability()` хранит канонический экземпляр `Abilities`, `abilityId()` возвращает
его стабильный `id()`. Для проверки конкретной способности использовать
`event.isAbility(<Name>Ability.CONSTANT)`, для категории — `event.kind()`.
Не добавлять имя способности в `GameEvent.Kind` и не вызывать `Kind.valueOf(ability.id())`.

Ядро создаёт запись через `GameEvent.abilityUsed(...)` и заполняет исполнителя,
цель, координаты и текст. `copiedAbility` содержит полученную копию, `borrowed`
отмечает применение сохранённой копии. Стратегия не добавляет запись в журнал сама.
Категория применения требует `ability`; перемещения, границы хода и реакции
не должны содержать `ability`, `copiedAbility` или `borrowed`.

В enum способности задать `eventTarget()` по смыслу `targetId`:

- `AbilityEventTarget.REQUIRED` — запись содержит ID фигуры-цели; это значение по умолчанию.
- `AbilityEventTarget.OPTIONAL` — способность применима к занятой или пустой клетке.
- `AbilityEventTarget.NONE` — запись не связывается с фигурой-целью.

Например, хук имеет `REQUIRED`, болото — `OPTIONAL`, телепорт — `NONE`.
`HeroTargeting` проверяет выбор клетки, а `eventTarget` — форму данных истории.
Эти политики задавать согласованно с механикой; наличие клетки не обязательно означает
наличие фигуры-цели. Ошибку применения не записывать как успешное событие.

`GameEventXml` сериализует общую категорию и отдельный ID. Новые ID не требуют
изменения кодека; чтение разрешает ID через реестр. Память применений и копий
восстанавливается из поля `ability`, независимо от имени категории.
Для нестандартного набора зарегистрированных описаний передать его стандартные
правила в `GameSaveFile.decode(bytes, defaults)`; обычная загрузка использует
описания из `HeroDefinitions`.

## 8. Порядок работы и критерии готовности

1. Зафиксировать механику: базовая шахматная фигура, способности, цели, стоимость,
   пассивные реакции и взаимодействия. Для миграции взять прежнее поведение за эталон.
2. Определить реализацию механики через контекст, запросы, эффекты и точки
   расширения этого контракта. Не изменять общие API при реализации отдельного героя.
3. Создать enum, Rules, кодек, описание и стратегию. Список брать через `getAbilities()`.
4. Добавить ID в `HeroType`, описание в `HeroDefinitions`; добавить каталог и UI.
   Сохранить совместимость истории и форматов. Не добавлять ветки героя в ядро.
5. Проверить поведение и интеграцию, затем обновить документацию героя.

Проверки выбирать по механике: допустимые и неверные цели, границы и препятствия,
нужные статусы, стоимость только при успехе, заряд и кулдаун, начальное назначение
совместимой фигуре, отсутствие мутаций при повторных предпросмотрах.
Для взятий проверить реакции и награды; для копируемых способностей — Ginseng;
для сохраняемого состояния — запись, загрузку и продолжение партии.
Регистрация должна сохранять уникальность ID и каноническую идентичность способностей.
Новую способность проверить через `Game`: успешное применение, категорию и ID события,
сохранение, загрузку и продолжение партии. Для копируемой способности проверить
получение и расход копии, в том числе после восстановления журнала.
Подсветка целей и выполнение запроса должны согласовываться.

Полный прогон из корня: `bash gradlew :composeApp:jvmTest`.
Только юнит-теста `preview` недостаточно для нового героя: проверить вызов через
`Game`, запись события и необходимые взаимодействия.
Не менять правила игры ради соответствия каркасу.
