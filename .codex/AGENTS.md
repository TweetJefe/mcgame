# Правила разработки mcgame

Эти инструкции действуют для всего проекта через корневой `AGENTS.md`.
Перед созданием или миграцией героя прочитать [HOW_CREATE_HEROES.md](HOW_CREATE_HEROES.md).
Документы и пояснения для разработчиков писать по-русски; имена Java/Kotlin API — по-английски.

## Обязательные правила кода

- При структурном рефакторинге сохранять наблюдаемое игровое поведение: правила,
  порядок причин отказа, стоимость, цели, кулдауны, заряды, реакции, историю и сохранения.
  Изменение баланса или исправление игровой механики — отдельная задача.
- Новый герой следует шаблону `AbstractHero`. Его поведение и неизменяемые правила
  размещаются в `game.heroes.<имя>`. Не создавать новые статические диспетчеры героев.
- Не добавлять в `Game`, `ActionEngine` и общие обработчики ветки по новому герою
  или его способности. Изменения общих контрактов выполнять отдельной согласованной
  задачей; агент, реализующий отдельного героя, использует установленный контракт.
- `Hero` не хранит изменяемое состояние фигуры или партии. Не кешировать исполнителя,
  цель, поле, номер хода или результат предыдущего действия в стратегии.
- `preview`, поиск целей, доступность и сообщения журнала не изменяют входные данные.
  Возвращать новые состояния и `HeroEffect`; применение результата — ответственность ядра.
- Поля правил делать неизменяемыми, коллекции публичных контрактов — неизменяемыми.
  Параметры баланса выносить в `*Rules`; проверять их допустимость при создании.
- Общие API принимают `Abilities`; конкретный герой использует собственный enum
  `*Ability implements Abilities`. Получать полный список через `*Ability.getAbilities()`.
- ID способностей стабильны и уникальны во всём реестре. Не менять ID ради переименования
  класса, константы или подписи. Не восстанавливать способности через общий enum.
- Переиспользовать Template Method: не копировать проверки базы и начисление заряда.
  Сохранять остальные поля `PieceState` при обновлении отдельных свойств.
- Для результатов использовать существующие `Success` и тематические `*Rejection`,
  реализующие `MoveResult`. Не возвращать коды строками и не восстанавливать общий enum.
- Писать читаемые методы с явными импортами и обычным форматированием.
  Убирать дублирование, когда у кода одна ответственность; не вводить абстракции без задачи.
  Комментарий объясняет инвариант или причину решения, а не пересказывает строку.
- Сохранять совместимость публичных фасадов и старых сохранений, пока их удаление
  не согласовано. Не менять формат сохранений молча.
- Не перезаписывать сторонние изменения и не смешивать документацию или перенос героя
  с посторонними правками. Обновлять эти инструкции при изменении согласованного контракта.

## Проверка изменений

Для игровой логики нужны проверки поведения: успешные и отклонённые действия,
стоимость, крайние цели, неизменность предпросмотра и применимые взаимодействия.
Проверки должны подтверждать правила игры, а не повторять устройство реализации.
При миграции существующего героя сохранять прежние регрессионные проверки.

Полный набор JVM-проверок: `bash gradlew :composeApp:jvmTest` из корня проекта.
Для итерации можно запускать тематические тесты через `--tests`; изменения общих
контрактов и подключения героя проверять полным набором. Документационные правки
проверять по исходникам и ссылкам; запускать игровые тесты ради одного текста не требуется.
Не ослаблять проверки ради успешного прогона. В отчёте указывать реально выполненную проверку.

## Архитектурные инварианты

- `Hero` — Stateless Strategy / Flyweight с неизменяемыми правилами. Состояние
  конкретной фигуры хранится в `PieceState`, данные действия — в `HeroActionContext`.
- `<Name>Hero extends AbstractHero` реализует специфику через Template Method.
  Общие проверки базы не дублировать и их порядок не менять.
- Герой связывается с совместимой базовой шахматной фигурой при начальном назначении;
  допустимые фигуры объявляются в `HeroDefinition`, проверка идёт через `Hero.supports`. Способности не заменяют
  шахматную личность фигуры, а копирование сохраняет личность исполнителя.
- Каждый enum `*Ability` предоставляет кешированный неизменяемый `getAbilities()`
  из `values()` через `Abilities.getAbilities(values())`. Общие API работают
  через интерфейс `Abilities`, а не общий enum способностей.
- Основной вход стратегии — `preview(HeroActionContext, AbilityRequest)`; база
  находит исполнителя и цель в контексте и вызывает единственный protected
  `previewAvailable(context, actor, target, request)`. Сохранять `destination`
  и `borrowed` при передаче запроса и подготовке операций.
- Схема выбора задаётся `HeroTargeting`: без цели, клетка или цель плюс назначение.
  Обе подсветки выводятся из полных `Hero.requests` через тот же предпросмотр
  и проверки продолжения хода. Не определять этап выбора по ID способности.
- Правила выбора целей принадлежат способности. Геометрия и эффект принадлежат герою.
  Подсветка целей и исполнение используют одну систему проверки запросов.
- Применение копии использует настоящего исполнителя и стратегию владельца из
  реестра партии. `AbilityUse` отделяет владельца правил и канал от личности фигуры.
  Не подменять `PieceState` и не создавать обнулённую копию `Rules`.
- Стоимость активации задавать `HeroEffect.withCost(AbilityCost...)`, отдельно от
  геометрии и обновлений состояния. База учитывает её один раз для `NATIVE` и
  пропускает для `BORROWED`, до операций и наград за взятия. Не списывать стоимость
  вручную и не восстанавливать поверх эффекта прежние ресурсы исполнителя копии.
- Длительные эффекты и их реакции принадлежат модулям механик по состоянию и ID
  настоящего исполнителя; они сохраняются после расходования копии. Пассивки
  исходного героя не копируются. Новая способность не требует веток в Ginseng.
- `HeroEffect` предлагает изменения, ядро подготавливает и проверяет результат,
  `Game` публикует успешное состояние. Герой не управляет бюджетом хода и журналом.
- `HeroType` содержит только идентичность героя: `PUDGE`, `ZEUS`, `GINSENG` и т. п.
  Суффиксы `_ROOK`, `_BISHOP`, `_PAWN`, `_KNIGHT` в именах героев запрещены. Название, допустимые начальные
  фигуры, тип и стандартные значения правил, кодек и фабрика принадлежат локальному
  `HeroDefinition<R>`. Описания регистрируются только в `HeroDefinitions`.
- Инициализацию и собственные ограничения состояния объявлять локальной неизменяемой
  `HeroStatePolicy<R>` в `HeroDefinition`. Она получает параметры партии и проверяет
  текущие формы, специальные поля и пределы ресурсов. Начальная совместимость
  `supportedBodies` и допустимые формы после превращений — разные правила.
- Новое состояние героя создавать через `HeroPieceFactory` с явным реестром партии.
  Призыв и превращение передают базовые данные и `PieceCreationContext`, сохраняя
  прежние правила переноса полей. Обычные обновления не запускают инициализацию заново.
- `PieceState` проверяет общие структурные инварианты, без списков конкретных героев.
  Специфические ограничения проверять через реестр при создании, на выходе предпросмотра,
  перед публикацией и загрузкой. Исходную клетку проверять по сохранённому происхождению;
  связи с другими фигурами и состояниями механик проверяются отдельно от собственной политики.
- `HeroRules` — неизменяемый типизированный контейнер. Стандартные параметры приходят
  из описаний; переопределения задаются через `with(definition, rules)`. Не расширять
  общий контейнер отдельными полями или геттерами для нового героя.
- Каждый герой предоставляет явный `HeroRulesCodec<R>` рядом с реализацией.
  Общий XML-слой обходит кодеки описаний; схема параметров не размещается в `GameSaveFile`.
- Применение любой способности записывается как `GameEvent.Kind.ABILITY_USED` с
  отдельным каноническим `Abilities ability`; стабильный ID доступен через `abilityId()`.
  Не добавлять имена способностей в `GameEvent.Kind` и не получать способность из имени категории.
- Форма `targetId` события задаётся в enum способности через `eventTarget()`:
  `REQUIRED`, `OPTIONAL` или `NONE`. Геометрия цели и идентичность цели в истории —
  разные части контракта. Историю публикует ядро, а не стратегия героя.
- Кодеки событий восстанавливают способности через реестр зарегистрированных описаний.
  Совместимость старых XML-имён изолирована в `GameEventXml`; новую способность туда не добавлять.
- Специальные состояния передаются через `MechanicStates` и `MechanicKey<S>`;
  не добавлять поле в `HeroActionContext`, `GameSnapshot` или `Game` для новой механики.
- `HeroDefinition.mechanics()` объявляет зависимости. `MechanicDefinition<S>` объединяет
  состояние, типизированные операции, реакции, события, кодек/восстановление и проверку.
  Новые модули подключаются зависимостями, без нового списка диспетчеризации в ядре.
- Шаги механик имеют явные фазы и зависимости `before` / `after`. Не менять порядок
  взаимодействий ради удобства переноса. Предпросмотр использует отдельную рабочую сессию.
- Операции из `onCaptured` выполняются до следующей гибели в общей очереди.
  Для взятия из обработчика использовать `MechanicSession.capture`, для собственной
  записи — `propose(MechanicEventDraft)`. Не начислять награду вручную.
- Специальные события используют `MECHANIC_EFFECT`, типизированные данные и локальный
  кодек; обычное взятие механикой — общую категорию `CAPTURE` и причину `MECHANIC`.
  Не расширять общие enum названием новой механики. Исторические псевдонимы принадлежат
  адаптеру совместимости и не являются шаблоном нового события.
- `HISTORY` и `END_HISTORY` не изменяют игровые состояния. Подготовка журнала
  завершается до публикации действия. Состояния новых механик сохраняются локальным
  кодеком либо полностью восстанавливаются из истории; `legacyWireState` для них запрещён.
- `HeroRegistry` неизменяем; результат `register` необходимо сохранять.
  Стратегии создаются фабриками зарегистрированных описаний с правилами партии.
  Индексы способностей строятся из `Hero.abilities()`.
- Собственная пассивная реакция героя возвращает эффект через `onCaptured`.
  Затем выполняются `MechanicDefinition.captureReactions()` по зависимостям;
  каждая получает актуальный `DeathContext`. Очередь последующих гибелей и
  начисление заряда обрабатываются общим механизмом.
- Участие и порядок новых каталогов задавать локальным `DraftProfile` описания.
  Начальные клетки выводятся из `supportedBodies`; не расширять общий список
  размещения. Драфт сохраняет состав и порядок в `DraftSnapshot.catalog()`.
  Не пересобирать сохранённый состав по текущему реестру и не изменять каталоги 1–10.
- Отображение размещать в локальном `HeroPresentation` и подключать через
  `HeroPresentations.all`. Java-движок не зависит от Compose и UI-реестра.
  Комплектность представлений проверять при подключении UI; изображения необязательны.
- Кнопки способностей строит общая `HeroPanel` из `Hero.abilities()`. Локальные
  виджеты используют `HeroPanelControls`, а не собственные вызовы `useAbility`.
  Не добавлять ветки героя в `ChessBoard` / `DraftScreen`; данные карточки,
  значки, подсказки и особые виджеты принадлежат локальному представлению.
- Подключение героя ограничено реализацией, конфигурацией, регистрацией, каталогом
  и отображением. Не добавлять его диспетчеризацию в общую игровую логику.
