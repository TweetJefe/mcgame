# Перед массовой миграцией героев

Документ для обсуждения и подготовки общей архитектуры. Здесь находятся недостатки
и задачи рефакторинга, вынесенные из инструкции создания героя.
Обязательный контракт реализации хранится отдельно в
[HOW_CREATE_HEROES.md](HOW_CREATE_HEROES.md), правила кода — в [AGENTS.md](AGENTS.md).

Каждый пункт обсуждаем по очереди: согласовываем решение, меняем общий контракт
и код, проверяем сохранение поведения, затем отмечаем результат здесь.
Ни один из пунктов ниже не считается решённым самим фактом его описания.

## 1. Идентичность героя и конфигурация правил

Статус: реализован и проверен 20 октября 2026 года.

Согласованные решения:

- `HeroType` остаётся общим enum для идентичности героя: `PUDGE`, `ZEUS`,
  `GINSENG` и т. п., без суффиксов шахматной фигуры.
  Добавление константы считается частью регистрации.
- Локальный `HeroDefinition<R>` объединяет название, совместимые начальные фигуры,
  тип правил, стандартные параметры, явный кодек и фабрику стратегии.
- `HeroRules` — неизменяемый типизированный контейнер; стандартные значения берутся
  из зарегистрированных описаний, настройки партии задаются переопределениями.
- Локальный `HeroRulesCodec<R>` читает и пишет параметры. Reflection не используется.

Реализовано:

- Все 16 идентичностей получили описания в своих пакетах; 13 настраиваемых героев — кодеки.
  `NONE`, `ILLUSION` и `BABA_YAGA` используют `NoHeroRules` без отдельной секции.
- `HeroDefinitions` содержит единственный список регистрации. `HeroRegistry.fromRules`
  создаёт стратегии через фабрики, без индивидуального подключения героев в методе.
- Имена констант очищены от шахматных суффиксов; старые строковые ID XML
  обслуживаются отдельным `HeroTypeCodec` в слое сохранений.
- `Hero.supports` и названия используют описание. Пудж передаёт своё описание в базу;
  существующее поведение других героев продолжает исполняться через прежние адаптеры.
- `HeroRulesXml` обходит кодеки; `GameSaveFile` не содержит схем параметров героев.
  Сохранены старые секции, атрибуты, порядок XML, стандартные и sandbox-профили.
  Старые конструкторы и геттеры `HeroRules` сохранены для совместимости; новые герои
  используют общий типизированный доступ и не требуют расширения этого API.
- `GoldRules` остаётся отдельной настройкой экономики, не параметром конкретного героя.

Проверка: `bash gradlew :composeApp:jvmTest` — 630 тестов без падений и пропусков.
Десять новых тестов проверяют независимую регистрацию, типы и изоляцию конфигураций,
кодеки, восстановление переопределений всех героев, отклонение некорректных секций
и совместимость прежних строковых ID с именами героев без шахматных суффиксов.
В отдельных процессах совпали 1371 запись сценариев Пуджа и 15 конфигураций правил
до/после рефакторинга: результаты, цели и SHA-256 полных XML, включая повторную загрузку.

Критерий завершения выполнен: идентичность и конфигурация подключаются регистрацией
описания и локального кодека, без новой игровой диспетчеризации в ядре.
Особые формы и статусы в `PieceState`, общие проверки `SnapshotValidator`, события,
копирование и каталог относятся к дальнейшим пунктам и не считаются мигрированными.

## 2. События способностей и совместимость истории

Статус: реализован и проверен 24 октября 2026 года.

- `GameEvent.Kind` больше не содержит 24 имени активных способностей.
  Любое применение имеет категорию `ABILITY_USED` и отдельный `Abilities ability`.
  Доступны `abilityId()`, `isAbility(...)` и фабрика `abilityUsed(...)`.
- `Game` публикует общее событие. Обработчики истории проверяют каноническую
  способность; `SpellState` читает её непосредственно, без поиска по `Kind.name()`.
  `SpellValidator` проверяет принадлежность через реестр с настройками партии.
- Политика `Abilities.eventTarget()` задаёт обязательный, необязательный или
  отсутствующий ID фигуры-цели. Общий валидатор истории не перечисляет способности.
- `GameEventXml` изолирует прежние XML-имена событий. Для существующих 24 ID
  сохранено прежнее представление версий 1–14 и точное повторное сохранение.
  Новые ID используют XML 15: `kind="ABILITY_USED"` и отдельный `abilityId`.
  При чтении ID и копии разрешаются через переданный реестр; неизвестные,
  неоднозначные и преждевременные поля отклоняются.
- Декодирование поддерживает явно переданный набор стандартных параметров
  зарегистрированных описаний через `GameSaveFile.decode(bytes, defaults)`.

Проверка: `bash gradlew :composeApp:jvmTest` — 639 тестов (597 Java + 42 UI),
без падений и пропусков. Девять новых тестов проверяют категорию/ID, согласованность
метаданных, старые события всех способностей, новый ID и ID, совпадающий с `MOVE`,
копирование/расход через журнал, защиту канала копии в старых форматах и сквозной
путь новой способности через `Game`, XML 15, восстановление и продолжение партии.
Повторное сравнение до/после: 1371 запись сценариев Пуджа и 15 конфигураций правил
совпали, включая SHA-256 XML и повторную загрузку.

Критерий завершения выполнен: новая зарегистрированная способность записывается
и восстанавливается без новой константы категории события.
Имена специальных реакций и существующий выбор метаданных рождения иллюзии
относятся к общим эффектам и дальнейшему переносу механик; они этим этапом не заменялись.

## 3. Контекст и эффекты специальных механик

Статус: реализован и проверен 24 октября 2026 года.

Согласованные решения:

- Герой возвращает типизированные операции; обработчики зарегистрированы модулем.
- Состояния механик находятся в неизменяемом контейнере с типизированными ключами.
- Порядок задаётся явными фазами и зависимостями, включая вложенные реакции.
- Один `MechanicDefinition<S>` связывает состояние, операции, реакции, события,
  кодек/восстановление и валидацию. Модули собираются из `HeroDefinition.mechanics()`.
- События механик имеют общую категорию, типизированные данные и локальный кодек.
  Совместимость прежних событий изолирована в адаптере.
- Предпросмотр изолирован; отклонённое действие не публикует состояния, ресурсы,
  ID, случайность, взятия, журнал и бюджет хода.

Реализовано:

- `HeroActionContext`, `ActionEngine.Context`, `GameSnapshot` и `Game` используют
  единый контейнер `MechanicStates`. Именованные API прежних состояний читают его;
  совместимые конструкторы сохранены.
- `HeroEffect.operations` передаёт неизменяемые операции. `MechanicRegistry` проверяет
  конфликты модулей, обработчиков, шагов, событий и зависимости до начала партии.
- Мины, болото, призыв, иллюзии, молнии, память способностей, видимость и экономика
  подключены отдельными модулями. `MechanicSession` координирует изолированный
  расчёт и ограниченное разрешение цепочек. Дублирующий `EffectResolver` удалён.
- Специальные ветки применения вынесены из `ActionEngine`; `Game` получает
  метаданные применения через стратегию, а историю и завершение хода — через модули.
  Проверки мин и иллюзий при перемещении также подключены фазами.
- `CaptureReactions` получает полный контекст состояний. Операции ответных реакций
  исполняются в точке гибели до следующей записи очереди, в том числе внутри мин,
  болот, молний и взрыва. Общее взятие новой механики доступно через `session.capture`.
- Специальные события в памяти используют `MECHANIC_EFFECT` и канонический
  `MechanicEventType<P>`. Старые константы реакций сохранены как входные псевдонимы
  для совместимости API; `kind()` возвращает общую категорию. `legacyKind()`
  обслуживает прежние реконструкторы и адаптеры. Новая механика их не расширяет.
- Новые состояния и данные событий используют XML 16 через общие кодеки.
  Прежние события продолжают записываться в старом виде с подходящей версией.
  Поддержано восстановление полностью выводимого состояния без второй копии в XML.
- Журнал готовится до публикации. Его обработчики не могут изменять игровое состояние.

Проверка: `bash gradlew :composeApp:jvmTest` — 650 тестов (608 Java + 42 UI),
без падений и пропусков. Одиннадцать новых тестов проверяют независимую механику через
`Game`, собственные состояния и события, зависимости и порядок обработчиков,
кодек и восстановление из истории, взятия и ответные реакции, загрузку и продолжение,
атомарный отказ операции/журнала, ограничение нестабильной цепочки и повреждённый XML.
Сравнение исходной и новой версий: совпали 1371 запись сценариев Пуджа и
15 конфигураций правил, включая SHA-256 полного XML и повторную загрузку.
Дополнительно совпали 686 записей для мин, молний, иллюзий, пряжи/горшка,
призыва и копья: все клетки, отсутствующие/внешние цели и цепочка молний
с завершением ходов, фиксированным RNG и повторной загрузкой.

Критерий завершения выполнен: новая механика подключает состояние, операции,
реакции, события, проверку и сохранение через свой модуль и зависимости описания,
без веток по герою в ядре. Обязательный контракт обновлён отдельно от этого плана.

Существующие стратегии продолжают использовать `LegacyHero` / `LegacyAbilityAdapter`.
Связанный набор прежних механик подключён через `HistoricalMechanics`;
`HistoricalJournal` изолирует старые правила записи. Пределы ресурсов после
пункта 7 принадлежат локальным политикам; `HistoricalBlindness` проверяет наложенную слепоту.
Их дальнейшее распределение по окончательным реализациям — задача массовой миграции.
Полный Template Method реализован в пункте 4. Универсальные правила копирования
остаются отдельным предметом пункта 5.

## 4. Полный запрос способности

Статус: реализован и проверен 24 октября 2026 года.

Согласованные и реализованные решения:

- Основной вход — `preview(context, request)`. `AbstractHero` находит исполнителя
  и цель из одного контекста, проверяет доступность и общую политику цели.
- Единственный обязательный protected-метод — `previewAvailable(context, actor,
  target, request)`. Пудж и тестовые стратегии переведены на него; старого
  protected-метода нет. `destination` и `borrowed` доступны без потерь.
- `Hero.requests` генерирует полные запросы. Обе стадии подсветки используют
  общий предпросмотр и прежнюю проверку продолжения хода.
  `getAbilityDestinations` принимает любую зарегистрированную способность.
- `HeroTargeting.Selection` явно задаёт отсутствие цели, одну клетку или цель
  плюс назначение. UI выбирает этапы по схеме и хранит первую клетку независимо
  от наличия фигуры. Список ID способностей без цели в обработчике копии удалён.
- Фаза `ABILITY_GUARD` при исполнении получает исходный полный запрос;
  самостоятельный запрос доступности сохраняет форму без выбранных целей.
- Публичные старые `preview`, `previewRequest`, `getDisplacementDestinations`
  и конструктор `HeroTargeting(boolean, Set)` сохранены как совместимые входы.
  Отдельный `preview` с переданными фигурами сохраняет прежнюю семантику
  отделённых состояний; новый игровой код использует контекст и полный запрос.
- Канал копии передаёт полный запрос в новый protected-метод Пуджа через
  `LegacyHeroes.previewBorrowedSource`. Старые стратегии используют прежний
  расчёт через адаптер; геометрия двухэтапной копии получает `destination`.
  На этапе 4 представление исполнителя, стоимость и расход копии не перерабатывались;
  их последующее изменение описано в пункте 5.

Проверки: `bash gradlew :composeApp:jvmTest` — 659 тестов (616 Java + 43 UI),
без падений, ошибок и пропусков. Независимая двухэтапная способность без веток в ядре; обе подсветки,
полный запрос в фазе механики; предпросмотр без мутаций; приоритет отказов;
нативное и скопированное перемещение, включая UI. В сравнении с исходной версией
совпали 9249 записей Ginseng: результаты, цели, клетки назначения, SHA-256 полного
XML после действий и его повторной загрузки. Начальное состояние PRNG зафиксировано;
неупорядоченный набор первых целей сравнивается в порядке координат.

Дополнительно совпали 1371 запись пяти сценариев Пуджа, 15 конфигураций правил
и 686 записей специальных механик с версией до этого этапа.

Критерий завершения выполнен: полный запрос проходит через стратегию; выбор обеих клеток,
предпросмотр и исполнение используют общий путь без определения этапа по ID.

## 5. Копирование способностей Ginseng

Статус: реализован и проверен 4 ноября 2026 года.

Согласованные и реализованные решения:

- Стратегия получает настоящий `PieceState`. `AbilityUse(owner, channel)` отделяет
  владельца правил и канал применения от личности фигуры. `ActionEngine` использует
  `ownerOf` реестра партии и общий `Hero.preview(context, request)` для обоих каналов.
- `AbilityCost` отдельно задаёт кулдаун и расход заряда активации. `AbstractHero`
  проверяет обычные ресурсы только для `NATIVE`, сохраняет специфические ограничения
  для копии и применяет стоимость после успешного расчёта, до операций и наград.
  Пудж переведён на этот контракт; protected-предпросмотр остаётся единственным.
- В `BorrowedEffects` нет временной шахматной фигуры, `freeRules`, центрального
  списка героев или восстановления полей поверх рассчитанного эффекта.
  Это совместимый фасад над реестром, в игровом пути он не нужен.
- Длительные последствия принадлежат настоящему исполнителю. Модули объявляют
  `captureReactions()` с зависимостями; они выполняются после собственной реакции
  героя, видят предыдущие изменения и завершают операции до следующей гибели.
- Проглатывание обслуживает `SwallowMechanic`, объявленный зависимостью описания
  Пуджа. Ginseng и остальные адаптеры больше не вызывают Пуджа для этой реакции.
  Правила жизни мины, молнии, призыва и прочих последствий сохранены.
- Сохраняются прежние получение, готовность, расход и замена копии, стоимость,
  награды, личности, статусы, геометрия, история и форматы сохранений.

Проверки: `bash gradlew :composeApp:jvmTest` — 666 тестов (623 Java + 43 UI),
без падений, ошибок и пропусков. Независимые новые способности получают настройки
партии, работают нативно и в копии, сохраняются и продолжаются после загрузки.
Новая длительная механика реагирует на гибель Ginseng после расходования и
восстановления копии. Проверены неизменность предпросмотра, цена, ограничения,
порядок реакций и отклонение неверных графов зависимостей.

С исходной версией совпали 45 570 записей всех 24 прежних копируемых способностей:
результаты, состояния фигур/механик, взятия и подготовленные события. Варианты:
слон/конь/ладья, собственный кулдаун и нулевой заряд, проглоченный союзник либо
пустой слот, все клетки и внешние/отсутствующие цели, вторая клетка перемещения;
начальный PRNG фиксирован. В отдельном сравнении совпали все 2811 записей
результатов, подсветки и SHA-256 полных XML-сохранений после реальных команд
Пуджа и Ginseng, включая повторную загрузку.

Критерий завершения выполнен: новая стратегия использует общий контракт копии
без новых исключений по имени способности. Обязательные правила обновлены отдельно.

Переходные границы: неперенесённые `LegacyHero` используют существующую локальную
диспетчеризацию и совместимые перегрузки утилит. Они принимают настоящего исполнителя;
их старые расходы ещё выражены локально через канал. При массовой миграции эти
расчёты переводятся на `AbilityCost` по обязательному контракту, без переноса адаптеров.
Старые публичные `previewBorrowed` / `previewBorrowedSource` сохранены фасадами;
игровой путь не использует их. Исторический набор механик сохраняет зависимость
проглатывания для совместимых регистраций; новое описание объявляет свои модули.

## 6. Каталог драфта и отображение

Статус: реализован и проверен 5 ноября 2026 года.

Согласованные и реализованные решения:

- `HeroDefinition` получает неизменяемый `DraftProfile`: доступность пиков и
  порядок. Все 13 прежних участников объявили профиль локально; обычная фигура,
  иллюзия и Баба-яга исключены из автоматического каталога.
- Новый `DraftCatalog` фиксирует состав и порядок по описаниям конкретной
  конфигурации. Начальные клетки проецируются из `supportedBodies()` на стандартную
  расстановку; отдельного списка героев для размещения нет.
- `DraftSnapshot.catalog()` сохраняется каждым действием и при восстановлении.
  Режим `DraftRules.CURRENT_CATALOG` используется новыми драфтами. XML 17 содержит
  явный список `HeroType`; расширение текущего набора не меняет сохранённый драфт.
  Каталог проверяется на соответствие описаниям конфигурации партии.
- Положительные номера 1–10 и старые записи обслуживает замороженный
  `LegacyHeroCatalog`. Составы, порядок, клетки и старое представление XML сохранены.
  `HeroCatalog` остаётся публичным фасадом; новые участники не добавляются в адаптер.
- `HeroPresentation` расположен рядом с UI героя и подключается через отдельный
  `HeroPresentationRegistry`. Движок не зависит от Compose. Проверка UI обнаруживает
  пропущенные/повторные представления; изображение необязательно.
- Общая `HeroPanel` строит собственные кнопки из `Hero.abilities()` реестра партии,
  использует доступность `Game`, схемы `HeroTargeting` и единый обработчик запросов.
  Локальные представления содержат тексты, значки, подсказки и расширения; слот копии
  Ginseng использует общие кнопки. В `ChessBoard` / `DraftScreen` нет списков героев
  и веток по конкретной способности. `Game.getHeroRegistry()` предоставляет тот же
  неизменяемый реестр, не создавая второй комплект стратегий для интерфейса.

Проверки: `bash gradlew :composeApp:jvmTest` — 675 тестов (629 Java + 46 UI),
без падений, ошибок и пропусков. Новое описание с другой исходной фигурой появляется
в каталоге и выбирается общим экраном; неизвестные производственным enum способности
выполняются через общую панель, включая третий скилл во втором ряду. Проверены
фиксация состава, привязка к конфигурации, строгая UI-регистрация и неверный XML.

С исходной версией совпали все 660 записей каталогов 1–10: состав, клетки,
результаты команд и состояние драфта. Сохранения каждой версии совпали побайтово
и прошли повторную загрузку. Все 114 прежних UI-снимков совпали попиксельно.
Изменение значения `catalogVersion` в проверках новых
драфтов отражает согласованный режим явного состава; игровые проверки сохранены.

Критерий завершения выполнен: подключение каталога и UI ограничено локальными
описаниями/представлениями и регистрацией, без нового списка в общих экранах.

Переходные границы: исторические описания `HeroCatalog.summary` и компоновки
версий 1–10 сохранены адаптерами для совместимости. Тексты и сведения старых панелей
перенесены без изменения игровых правил. Специфическая инициализация и валидация
`PieceState`, включая исходный цвет, остаются отдельным пунктом 7 и не менялись
в рамках UI. На этапе 6 массовая миграция ещё не запускалась.

## 7. Инициализация и проверка состояния героя

Статус: контракт согласован 5 ноября 2026 года; реализован и проверен.

- Локальная неизменяемая `HeroStatePolicy<R>` подключается через `HeroDefinition`.
  Она инициализирует собственные поля и проверяет текущие формы, исходный цвет,
  специальные статусы/ссылки и пределы ресурсов по параметрам партии.
- `PieceState` сохраняет общие инварианты; конкретные `HeroType` больше не
  перечисляются в его конструкторе и начальной инициализации. `HeroStateConstraints`
  переиспользует проверки без знания списка героев.
- `HeroPieceFactory` получает явный `HeroRegistry`, базовые данные и
  `PieceCreationContext`. Начальное назначение, призыв, создание иллюзии и
  превращение используют общий путь, сохраняя прежние правила переноса полей.
  При обычном обновлении инициализация не повторяется.
- `supportedBodies` остаётся ограничением начального назначения; текущие формы
  проверяет политика. Превращения пешек, эволюция и формы копирующего героя сохранены.
- Реестр проверяет результаты предпросмотра, применение после подготовки истории,
  завершение хода и снимок перед сохранением/загрузкой. `DraftValidator` передаёт
  исходную клетку локальной политике без списка цветозависимых героев.
- Политики подключены всем существующим описаниям до миграции стратегий.
  Пределы собственных ресурсов больше не диспетчеризуются через
  `HistoricalResources`; наложенную слепоту пока проверяет `HistoricalBlindness`.
  Связность проглатывания, болота и иллюзий проверяется отдельно от политики.
- `PieceState.initial` сохранён как адаптер стандартной конфигурации. Прежние
  публичные входы `SummonResolver` делегируют фабрике; рабочие модули передают
  реестр своей партии. Формат сохранений не изменялся.

Проверки: 4 816 сочетаний исходной инициализации, форм, статусов, исходного цвета
и ссылок дают те же результаты допустимости, что исходная версия; 45 570 проверок
копий и 2 811 проверок команд/сохранений совпали, включая состояния, события и XML.
Все 116 изображений UI совпали попиксельно.
Добавлены проверки локальных параметров, происхождения, недопустимого результата
инициализации/стратегии/конца хода и отказа загрузки. Полный JVM/UI-набор: 685 тестов, без падений, ошибок и пропусков.

## Единый API после массовой миграции

Все 16 описаний создают собственные стратегии на базе `AbstractHero`: 13 игровых
героев и `NoneHero`, `IllusionHero`, `BabaYagaHero` для служебных сущностей.
Внутренние `LegacyHero`, `LegacyHeroAbilities` и `LegacyAbilityAdapter` удалены.

После завершения миграции пользователь отказался от поддержки старого API.
Удалены `LegacyPreview`, `HeroAbilities`, `LegacyHeroes`, `BorrowedEffects`,
13 локальных `*Abilities`, detached-методы героев и перегрузки
`Hero.preview(..., actor, target, ...)` / `previewRequest`, а также
специальный фасад `Game.getDisplacementDestinations`. Единственный вход
предпросмотра — `Hero.preview(HeroActionContext, AbilityRequest)`.
Геометрические помощники, используемые валидаторами и журналом, вызываются
непосредственно у локальных `*Hero`. Тесты используют полный контекст и запрос.

Из тестового набора удалены только пять проверок совместимости упразднённого API.
Проверки игровых эффектов, статусов, наград, стоимости, копий, неизменности
предпросмотра, закрытости ядра и расширяемости переведены на действующие контракты.
Полный набор: **714 тестов**, без падений, ошибок и пропусков. С предыдущей версией
совпали 58 060 записей собственных способностей, 45 570 записей копий,
1 842 записи команд/XML/загрузки/доступных ходов и 2 811 прежних игровых сценариев.

`game.mechanics.compat` сохраняет взаимосвязи прежних модулей, исторические записи
и XML-псевдонимы. Это совместимость данных сохранений; старый API способностей
не поддерживается. Формат сохранений при удалении API не менялся.

## История и проверенная исходная точка

20 октября 2026 года восстановлены функциональные изменения, потерянные при merge

игровых ошибок. Подключение полного контракта Пуджа через реестр выполнено;
