# Драфт матча: выбор, часы и подготовка

Backend новой схемы — `game.draft.MatchDraft`. Игрок 1 соответствует белым, игрок 2 — чёрным. Определение цвета и места игрока в сетевой комнате остаётся ответственностью комнаты.

## Последовательность

`1 бан → 2 бан → 2 пик → 1 пик → 1 пик → 2 пик → 2 бан → 1 бан → 1 пик → 2 пик → 2 пик → 1 пик → 1 бан → 2 бан → 1 пик → 2 пик`.

Всего 16 действий: по три бана и пять пиков у каждого игрока. Баны и пики общие: выбранный или забаненный герой недоступен обеим сторонам. Закончить пики досрочно нельзя. Фазы сессии: `SELECTION → PREPARATION → COMPLETE`. Внутри выбора ожидаемые сторона и действие задаются `Snapshot.expected`.

## Состав

У каждого игрока обязательно **2 героя-пешки, 1 герой-слон, 1 герой-конь, 1 герой-ладья**. Их можно выбирать в любом порядке. Роль определяется совместимым исходным телом из `HeroDefinition`, без перечисления имён героев.

Каждый предлагаемый бан или пик проходит проверку возможности заполнить оставшиеся роли **обоих** игроков. Если коня ещё не выбрал один игрок, в общем пуле должен оставаться хотя бы один конь; если оба — хотя бы два. То же действует для слонов, ладей и оставшегося количества пешек. Поэтому нельзя ни забанить последнего нужного героя, ни выбрать себе лишнюю фигуру занятой роли. `availableHeroes()` возвращает только допустимые варианты; прямые команды проверяются тем же правилом.

## Часы

- На каждое новое действие даётся 20 секунд, включая два последовательных действия одного игрока.
- У каждого игрока отдельный запас 60 секунд на **весь** драфт. Он расходуется только после основных 20 секунд и не восстанавливается.
- Например, действие длиной 30 секунд оставляет 50 секунд запаса. Следующее действие снова получает основные 20 секунд.
- После исчерпания основных секунд и всего оставшегося запаса выполняется автоматическое допустимое действие. Выбор детерминированный: первый допустимый герой в зафиксированном каталоге. Квоты сохраняются.
- При команде ровно на границе истечения первым выполняется автоматическое действие.

Просроченная команда получает `ACTION_EXPIRED`, даже если следующее действие — снова пик этого игрока. Она не выполняет второй выбор поверх автоматического.

Часы монотонные, по умолчанию `System.nanoTime`; для тестов передаётся `LongSupplier`. Серверный планировщик должен регулярно вызывать `tick()`, даже без входящих команд. Команды также проверяют истёкшее время перед применением. Пропущенные вызовы планировщика не перезапускают сроки: один `tick` последовательно обрабатывает все прошедшие границы.

`getSnapshot()` показывает оставшиеся основные секунды, оба запаса, текущий этап и журнал, но сам не выполняет автоматические выборы и не списывает запас повторно. `actions` содержит настоящую смешанную последовательность, длительность и признак автоматического действия.

## Подготовка

После последнего пика одновременно для обоих игроков начинаются **15 общих секунд** подготовки. На пиках клетка не выбирается. `placementTargets(side, hero)` возвращает свободные совместимые стартовые клетки:

| Роль | Белые | Чёрные |
| --- | --- | --- |
| Пешка | a2–h2 | a7–h7 |
| Конь | b1, g1 | b8, g8 |
| Слон | c1, f1 | c8, f8 |
| Ладья | a1, h1 | a8, h8 |

`place` разрешает разместить только своего выбранного героя, без наложения фигур. Можно поменять свободную клетку или снять размещение через `clearPlacement`. Оба игрока расставляются независимо; очереди действий в подготовке нет. Даже если всё расставлено раньше, стадия заканчивается по общему сроку 15 секунд.

По истечении срока нерасставленные герои занимают первые свободные подходящие клетки. Ручные назначения сохраняются. Затем `completedDraft()` предоставляет конечный состав. До завершения подготовки этот метод и запуск партии отклоняются.

## Подключение к игре и совместимость

```java
MatchDraft draft = new MatchDraft();
draft.ban(FigureColor.WHITE, hero);
// Последующие команды — согласно snapshot.expected().
draft.tick(); // Регулярно вызывается сервером.
// После COMPLETE:
Game game = Game.mobaFromDraft(draft, 600, System::nanoTime);
```

Снимки и публичные коллекции неизменяемы. Изменения сессии синхронизированы, недопустимые команды не принимаются; объективно истёкшие часы при этом могут вызвать автоматический переход.

`Draft` / `DraftSnapshot` оставлены для чтения старых сохранений и представления конечного исходного состава внутри `Game`. При завершении новой сессии создаётся совместимый конечный снимок с тремя банами и пятью пиками на сторону. Его служебный журнал группирует баны перед пиками, чтобы действующий загрузчик мог восстановить его; **он не заменяет настоящий хронологический журнал `MatchDraft.actions`**. Если серверу нужно хранить историю лобби, сохранять её отдельно.

Незавершённая сессия и её часы пока живут в памяти; восстановление после перезапуска сервера этим API не реализовано. Сохранение начатой игры и первоначального состава работает через существующий XML без изменения формата.

Этот этап реализует backend. Старый экран Compose использует прежний `Draft`; будущий интерфейс LibGDX должен обращаться к `MatchDraft`, показывать его часы и использовать `placementTargets` для подсветки. Отрисовка и сетевые обработчики здесь не добавлялись.

Включены 15 новых проверок: порядок действий, состав, защита оставшихся коней и ладей, превышение квот, часы и резерв, границы таймаутов, просроченные команды, автоматическое завершение, подготовка, неизменяемость снимков, запуск игры и загрузка конечного состава.
