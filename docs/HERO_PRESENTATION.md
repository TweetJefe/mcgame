# Драфт и отображение героев

Игровое описание и отображение регистрируются независимо. `HeroDefinition<R>`
содержит игровые данные, фабрику и `DraftProfile`; Compose-код расположен в
`org.chess.heroes.<имя>`. Java-движок не загружает и не проверяет UI-реестр.
Обязательный контракт: [HOW_CREATE_HEROES.md](../.codex/HOW_CREATE_HEROES.md).

## Состав драфта

`DraftProfile.pickable(order)` включает описание в новые каталоги.
`DraftProfile.EXCLUDED` исключает его из автоматического набора; это значение
по умолчанию. Обычные фигуры, иллюзии и призываемые сущности не являются пиками.
`withDraftProfile` возвращает новое описание; вызывать его при объявлении
`INSTANCE`, до регистрации и создания `HeroRules`.

`DraftCatalog.current(configuration.definitions())` сортирует участников по
`order`, затем по стабильному имени `HeroType`. Стартовые клетки вычисляются
на стандартной доске из `supportedBodies()` и стороны. Совместимость начальной
фигуры не используется как проверка формы после превращения или копирования.

`DraftRules.CURRENT_CATALOG` означает явный состав нового драфта. Двухаргументный
конструктор `DraftRules` использует этот режим. Ограничение банов по размеру
каталога проверяется при создании снимка с фактическим составом; числовые границы
правил проверяются в самом `DraftRules`.

`DraftSnapshot.catalog()` сохраняет неизменяемые состав и порядок. Следующее
действие передаёт тот же каталог; повторно собирать его из текущего реестра нельзя.
`Draft(rules, configuration)` строит каталог из описаний конкретной конфигурации;
`Draft(rules, catalog, configuration)` принимает явный набор. Сохранённый состав
можно восстановить через `Draft.fromSnapshot(snapshot, configuration)`; все его
описания должны соответствовать конфигурации партии.

XML 17 записывает список канонических `HeroType` в `draft/catalog/hero@id`.
При чтении он привязывается к зарегистрированным описаниям без добавления новых
участников из текущего набора. Неизвестные и повторяющиеся ID отклоняются.
Каталоги 1–10 неизменны и обслуживаются `LegacyHeroCatalog`; их положительные
номера и прежний формат записи сохраняются. Добавление героя не требует нового
номера каталога или изменения исторического адаптера.

## Локальное представление

Создать `<Name>Presentation` в `org.chess.heroes.<имя>`, реализующий
`HeroPresentation` либо наследующий `BaseHeroPresentation`, и зарегистрировать
его в `HeroPresentations.all`. Реестр отклоняет дубликаты и отсутствие требуемого
представления при подключении UI. В `ChessBoard` и `DraftScreen` ветки по герою
или способности не добавляются.

| Часть | Ответственность |
| --- | --- |
| `type`, `shortName`, `summary`, `badge` | Идентичность, короткая подпись, описание карточки, текстовый значок |
| `draftSummary(rules)` | Описание карточки с учётом параметров партии |
| `boardBadge(context)` | Динамический текст значка по состоянию фигуры |
| `title(context)` | Заголовок выбранной фигуры; по умолчанию имя игрового описания |
| `label(ability)` | Подпись общей кнопки; по умолчанию `ability.displayName` |
| `ultimateCaptures(rules)` | Порог заряда для пояснения каталога, если он применим |
| `Details(context)` | Локальные строки состояния перед общими кнопками |
| `AfterActions(context)` | Пояснения выбора после кнопок |
| `Extra(context, controls)` | Особые сведения и необязательные локальные виджеты |
| `Portrait()` / `CellDecoration(context)` | Необязательные локальные изображения и декорации |

`HeroViewContext` предоставляет снимок, фигуру, выбранную способность и
неизменяемый реестр самой партии. В панели фигура берётся из снимка; на клетке
используется представление с учётом видимости и маскировки. Для чисел баланса использовать типизированные
`context.snapshot.heroRules().get(<Name>Definition.INSTANCE)`; не добавлять
ради нового героя геттер в общий контейнер.

Изображения и их загрузку размещать у локального представления. Они необязательны:
текстовый значок и название обеспечивают базовое отображение. Ядро и его
сохранения не зависят от путей ресурсов, Compose-компонентов и размеров элементов.

## Общие команды

`HeroPanel` получает собственные способности через `Hero.abilities()` из реестра
партии. Кнопки располагаются рядами по две; локальное представление не перечисляет
их повторно и не реализует собственный обработчик применения.

`HeroPanelControls.AbilityButton` получает доступность из `Game` и передаёт выбор
в общий обработчик `ChessBoard`. `Rejection` отображает ту же причину отказа.
Для действия скопированной способностью виджет указывает `borrowed = true`;
пример — `GinsengPresentation.Extra`.

Общий обработчик использует `HeroTargeting`: немедленный запрос без цели,
выбор одной клетки или выбор цели и клетки назначения. Подсветка берётся у `Game`.
Представление не рассчитывает законность, геометрию, стоимость или изменения
игрового состояния. Оно не вызывает `Game.useAbility` напрямую.

`beforeInventory`, `showRejections`, `hideBudgetRejection` и `retainSelection`
управляют расположением и обратной связью панели, не меняя игровых разрешений.
Для нового героя использовать стандартную панель; локальное расширение добавляет
нужные сведения или виджет через общие элементы управления.

## Проверка

Проверить участие и порядок в новом каталоге, совместимые клетки, неизменность
сохранённого состава при расширении реестра, сохранение/загрузку и продолжение.
В UI проверить регистрацию представления, подписи, выбор целей и выполнение через
общую панель. Новая способность должна работать без её имени в общих экранах.

Проверки этапа 6: 675 тестов; 660 записей сравнений версий 1–10 совпали с исходной
реализацией, включая побайтовую запись и повторную загрузку старых сохранений.
Все 114 прежних UI-снимков совпали попиксельно.
