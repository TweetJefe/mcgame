# Подключение Пуджа через объектный контракт

Этап выполнен 20 октября 2026 года после восстановления исходной сборки:
[BUILD_BASELINE.md](BUILD_BASELINE.md).

## Работающий игровой путь

`Game` создаёт неизменяемый `HeroRegistry.fromRules(heroRules)` один раз при создании
или восстановлении партии. Каждый тип получает переиспользуемую стратегию для этих
правил. Все подготовленные `ActionEngine.Context` сохраняют тот же реестр.

Для Пуджа используется `game.heroes.pudge.PudgeHero`, наследующий `AbstractHero`.
Ядро получает поведение через `registry.get(actor.hero())` и использует:

- `supports` при проверке начального назначения героя фигуре;
- `abilities`, `availability`, `targeting` и `requests` для доступности и поиска целей;
- `preview` для расчёта эффекта и стоимости;
- `afterCapture` для начисления заряда;
- `onCaptured` для подготовки реакции на гибель;
- `abilityMessage` для прежнего текста журнала успешного применения.

`HeroTargeting` описывает форму запроса и разрешённые исключения. Общая проверка
сохраняет порядок причин отказа: лишняя клетка назначения, форма/границы цели,
выбор себя, невидимость, король, иллюзия, горшок, коробка.
Геометрия хука, списание заряда, проглатывание и проверка пересечения болота
реализованы в `PudgeHero`.

`HeroActionContext` предоставляет только публичные неизменяемые данные: поле,
состояния фигур, номер хода, местность, видимость, память способностей и экономику.
Конструктор из трёх исходных аргументов сохранён для самостоятельных предпросмотров.
Контекст реакции на гибель содержит подготовленные состояния; поле в нём также
служит фабрикой отделённых шахматных фигур для описания взятий.

## Реакции на гибель

`CaptureReactions` управляет ограниченной очередью событий гибели и не выбирает
конкретного героя. Для каждого события вызывается зарегистрированный `Hero.onCaptured`.
Возвращённые изменения и взятия обновляют временное состояние; последующие гибели
помещаются в очередь с сохранением их порядка и клеток. Выживший исполнитель
ответного взятия врага получает заряд через свою стратегию.

`PudgeHero.onCaptured` освобождает проглоченного союзника и предлагает ответное
взятие убийцы. Сохранены проверки короля, отсутствующего/погибшего убийцы, горшка,
некорректной ссылки на союзника и различие `CAPTURED` / `DESTROYED`.
Копия проглатывания у Ginseng использует ту же реакцию.

Временный адаптер Ares сохраняет прежний приоритет мести. Общая очередь
обрабатывает дальнейшие реакции погибшего убийцы без рекурсии.

## Совместимость и границы этапа

- `HeroAbilities` стал фасадом над реестром, без собственной диспетчеризации.
- `PudgeAbilities` делегирует новому герою. Исходный самостоятельный callback API
  `captureReaction(..., UnaryOperator<PieceState>)` сохранён через совместимый метод
  в `PudgeHero`; обычная игра использует `onCaptured`.
- Остальные герои подключены через пакетные адаптеры `LegacyHero` /
  `LegacyHeroAbilities`. Их миграция продолжается отдельно; адаптеры не обслуживают Пуджа.
- Общие проверки целей и поиск запросов вынесены за интерфейс `Hero`. Активные
  механики некоторых оставшихся героев, обработка их состояний и часть метаданных
  событий пока остаются в ядре. Полная цель «новый герой по шаблону + реестр + отображение»
  ещё не достигнута для всех возможных механик.
- Правила, баланс, ID фигур, бюджеты хода и формат сохранений в этом этапе не менялись.

## Проверка поведения

Стандартная команда:

```sh
bash gradlew :composeApp:jvmTest
```

Результат: **617 тестов, 0 падений, 0 ошибок, 0 пропусков** — 575 Java-тестов
и 42 теста интерфейса в 59 тестовых классах.

Добавлены семь тестов: неизменяемость и конфигурация реестра, неоднозначная
регистрация, порядок отказов при выборе целей, делегирование запросов и эффектов
из `ActionEngine`, вызов зарегистрированной реакции общей очередью гибелей.
Существующий набор продолжает проверять копии Ginseng, цепочки с Ares,
срабатывание болот и мин, бюджеты, UI и совместимость сохранений.

Дополнительно версия до подключения и новая версия запускались отдельными Java-процессами
с одинаковыми командами и фиксированным временем на всех пяти `PudgeScenario`.
Сравнивались результаты, доступные цели и SHA-256 полных XML-сохранений после команд;
каждое сохранение также проверялось повторной загрузкой и записью без изменений.
Проверены все 64 клетки, отсутствующая и внешние цели, лишняя клетка назначения,
а также полные последовательности учебных сценариев, включая освобождение союзника.
Все **1371 записи сравнения совпали**.
