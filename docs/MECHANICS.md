# Контракт специальных механик

Механика подключается через `HeroDefinition.mechanics()`. Её
`MechanicDefinition<S>` объединяет типизированное состояние, операции,
реакции, события, проверку и сохранение. Несколько героев могут зависеть от
одного модуля. `HeroRegistry.mechanics()` собирает весь граф зависимостей.

Обязательный контракт героя: [HOW_CREATE_HEROES.md](../.codex/HOW_CREATE_HEROES.md).
Результаты этапов и переходные реализации: [BEFORE_MIGRATE_ALL_HEROES.md](../.codex/BEFORE_MIGRATE_ALL_HEROES.md).

## Состояние и операции

Состояние — неизменяемый record или класс. `MechanicKey<S>` содержит стабильный
ID, `Class<S>` и неизменяемое начальное значение. Модуль объявляет один экземпляр
ключа. `MechanicStates` возвращает начальное значение отсутствующего ключа;
`with(key, next)` создаёт новый контейнер. Стандартные значения не дублируются
внутри контейнера. Подмена ключа с тем же ID отклоняется.

Контекст героя и снимок партии содержат один контейнер. В `Game` также нет
отдельных полей каждого специального состояния. Именованные геттеры прежних
состояний делегируют `BuiltInStates` и сохраняют совместимость API.

Герой возвращает `HeroEffect`: результат, обновления фигур, взятия и операции.
Например, операция установки объекта может выглядеть так:

```java
public record PlaceMarker(long ownerId, Position square) implements MechanicOperation {}
```

Модуль регистрирует `MechanicHandler<PlaceMarker>`, указывает его ID, фазу,
зависимости и функцию `(session, operation) -> MoveResult`. Класс операции
имеет ровно одного обработчика в реестре. Операция содержит данные, а не callback,
изменяющий живую партию. Операции не сериализуются: сохраняется результат действия.

`MechanicSession` создаётся отдельно для каждого предпросмотра. Она предоставляет:

- `before()` — исходный контекст; `context()` — подготовленные фигуры и состояния;
- `state(KEY)` / `state(KEY, next)` — состояние механики;
- `pieces()`, `pieces(next)`, `update(updates)` — подготовленные фигуры;
- `local(KEY)` / `local(KEY, next)` — временные данные одного расчёта;
- `capture(actorId, victimId)` — общее взятие с зарядом и ответными реакциями;
- `propose(draft)` — предложенную запись собственного события;
- `rules()`, `heroes()`, `side()`, `turn()` — неизменяемую конфигурацию действия.

Занятость читать из `context().pieces()` / `pieceAt`: `Field` остаётся исходной
геометрией и фабрикой фигур. Сессию и её данные нельзя сохранять в полях стратегии
или модуля. Для каждой операции вернуть новый `MoveResult`; отказ отменяет весь
подготовленный результат, включая случайность, ID, награды и записи.

## Порядок реакций

`MechanicPhase` задаёт явные границы назначения, перемещения, способности,
входа на клетку, стабилизации, наград, завершения хода и формирования истории.
`MechanicStep.before` / `after` и одноимённые поля обработчика ссылаются на ID
шагов той же фазы. Реестр проверяет существование ссылок и отсутствие циклов.
Независимые шаги упорядочиваются по стабильному ID, а не по порядку регистрации.

`ENTRY` повторяется до стабилизации фигур и состояний. Число проходов ограничено;
нестабильная цепочка возвращает `INVALID_BOARD`, не публикуя частичный результат.
В существующем наборе сначала обрабатываются мины, затем болото, отложенный взрыв
и призыв. Реакции на гибель могут происходить внутри этих шагов.

`CaptureReactions` вызывает собственную пассивную `Hero.onCaptured`, затем
`MechanicDefinition.captureReactions()` в порядке зависимостей `before` / `after`.
Каждая `MechanicCaptureReaction` получает `DeathContext`: жертву до удаления,
ID убийцы, клетку гибели и актуальный контекст подготовленных фигур и механик.
Реестр отклоняет повторные ID, неизвестные зависимости и циклы.
Реакция проверяет своё состояние и возвращает `HeroEffect`; отсутствие эффекта
выражается через `HeroEffect.empty()`. Каждая видит результат предыдущей. Операции её эффекта выполняются
синхронно в точке гибели, перед следующей гибелью в очереди. Обработчики операций
используются те же; их обычная фаза не откладывает ответную реакцию до конца действия.

`HISTORY` и `END_HISTORY` формируют только записи. Изменение фигур, состояний или
взятий в этих фазах отклоняется. Журнал и метаданные готовятся до публикации `Game`.

## События

`MechanicEventType<P>` объединяет стабильный ID, тип неизменяемых данных,
явные функции кодирования/декодирования и `MechanicEventPolicy`.
Политика определяет связь с активным ходом и обязательность исполнителя,
цели и координат. Проверку смысла данных реализует модуль.

`type.event(payload)` создаёт типизированный `MechanicEvent<P>`.
`MechanicEventDraft` добавляет ход, сторону, ссылки, координаты и текст.
Обработчик вызывает `session.propose(draft)`; номера назначает общий путь.
`GameEvent` хранит категорию `MECHANIC_EFFECT`, а ID и данные — отдельно.
`event.isEffect(TYPE)` проверяет канонический зарегистрированный тип.

Общее взятие новой механикой имеет категорию `CAPTURE` и
`Capture.Cause.MECHANIC`. Награды и удаление статусов обрабатываются общим путём;
собственное событие описывает причину воздействия. Не добавлять имя новой
механики или способности в общие enum.

## Сохранение и проверка

`MechanicStateCodec<S>` задаёт явный набор строковых полей и создаёт валидированное
типизированное состояние. Если состояние полностью выводится из истории,
переопределить `restore(snapshot)`: отдельная копия в XML не нужна.
Без кодека запись проверяет равенство состояния результату восстановления.
Модули восстанавливаются после своих зависимостей.

`validate(snapshot)` проверяет согласованность состояния с фигурами, правилами
и журналом. Не полагаться только на правильность синтаксиса XML. При развитии
собственной схемы её версию и миграцию обрабатывает локальный кодек.

Новые состояния записываются общей секцией XML 16 `mechanics/state`, новые
события — категорией `MECHANIC_EFFECT`, атрибутом `effectId` и элементом `data`.
Общий XML-слой обходит зарегистрированные кодеки. Неизвестные ID, неоднозначные
регистрации, повторные состояния и поля, отсутствующие данные и преждевременная
версия отклоняются. Имена Java-классов из файла не загружаются.

Проверки механики должны проходить через `Game`: успешное и отклонённое действие,
повторный предпросмотр без мутаций, применимые цепочки реакций, событие,
сохранение, загрузку и продолжение партии. Регрессионные правила существующего
героя сохраняются при переносе.

## Стоимость и копии

Стратегия получает настоящего исполнителя. Владелец правил и канал задаются
`AbilityUse`, данные выбора — полным `AbilityRequest`. Общий шаблон применяет
`AbilityCost` при нативной активации, пропускает её для копии и очищает стоимость
до обработки операций. Модуль не списывает повторно кулдаун или заряд активации;
его эффекты и награды за взятия работают с настоящим исполнителем.

Длительные состояния привязаны к ID исполнителя и не зависят от наличия копии
в его слоте. `SwallowMechanic` обрабатывает ссылку на союзника в `PieceState`;
мины, молнии и призыв используют свои типизированные состояния. Собственные
пассивные способности исходного героя исполнителю копии не передаются.
