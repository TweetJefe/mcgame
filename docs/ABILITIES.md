## Общий контракт

`Abilities` предоставляет стабильный `id()`, подпись `getDisplayName()` и правила
целей `targeting()`. Общие API (`Hero`, `AbstractHero`, `AbilityRequest`, `Game`,
история, копии Ginseng) принимают этот интерфейс. Код конкретного героя использует
свой enum, например `PudgeAbility.HOOK`.

В enum находятся идентичность и метаданные способности. Расчёт эффектов и работа
с правилами остаются в `PudgeHero` и реализациях других героев.
`AbstractHero` принимает `List<? extends Abilities>`, поэтому можно передавать
списки конкретного enum, сохраняя неизменяемую копию внутри базы.

Каждый enum хранит один неизменяемый список всех своих констант и предоставляет
статический `getAbilities()`. Список автоматически собирается из `values()` в порядке
объявления через общую фабрику `Abilities.getAbilities(values())`. Например,
конструктор `PudgeHero` передаёт в базовый класс `PudgeAbility.getAbilities()`.
Старые фасады `*Abilities.abilities()` делегируют этим спискам.
Java не позволяет требовать статический метод у реализаций интерфейса:
`Abilities.getAbilities(...)` — фабрика, а методы enum — единообразная договорённость.

## Полный запрос и выбор клеток

`AbilityRequest(actor, ability, target, destination, borrowed)` — единый вход
`Hero.preview(context, request)`. `AbstractHero` проверяет доступность и общую
политику целей, затем передаёт найденные фигуры и полный запрос в единственный
protected `previewAvailable(context, actor, target, request)`.

`HeroTargeting.Selection` задаёт схему: `NONE`, `SQUARE`, `TARGET_AND_DESTINATION`.
Фабрики — `untargeted()`, `square(...)`, `targetAndDestination(...)`.
Вторая клетка и канал копии передаются в стратегию и сессию механик.
Геометрию, обязательность и допустимость второй клетки проверяет герой с
сохранением порядка причин отказа. Политика целей не задаёт дальность и препятствия.

`Hero.requests` генерирует полные запросы-кандидаты. `Game.getAbilityTargets`
и `getAbilityDestinations(actor, ability, target, borrowed)` фильтруют их через
тот же предпросмотр и проверку продолжения хода, что используется при применении.
Интерфейс определяет количество этапов по схеме, без сравнения с ID способности.
Старый `getDisplacementDestinations` делегирует общему методу.

## Регистрация и ID

`HeroRegistry` автоматически строит индексы из `Hero.abilities()`:

- `abilityById(id)` возвращает зарегистрированную константу либо отклоняет неизвестный ID;
- `findAbility(id)` возвращает null для событий, которые не являются применением способности;
- `ownerOf(ability)` возвращает владельца зарегистрированного экземпляра;
- регистрация отклоняет пустые ID и совпадение ID даже у констант разных enum.

Чтобы добавить способность, нужно объявить её в enum героя: `getAbilities()`
автоматически включит новую константу в `Hero.abilities()`.
Отдельного центрального списка для поиска и разбора ID нет.
Общие неизменяемые метаданные `HeroRegistry.standard()` строятся той же фабрикой,
что используется для игровых реестров с конкретными правилами.

ID задаётся явно. Он не должен меняться при переименовании класса, enum-константы
или отображаемого текста. Все 24 прежних значения сохранены без изменений.

## Сохранения, история и копии

XML пишет `Abilities.id()` вместо неявного `Enum.toString()`. При чтении поле
`copiedAbility` разрешается через реестр, без `Enum.valueOf` и общего enum-класса.
Версии формата и существующие значения атрибутов не изменены.

`SpellState` восстанавливает способности по ID событий и хранит интерфейс `Abilities`.
Копирование сохраняет исходную константу enum, поэтому скопированный хук остаётся
`PudgeAbility.HOOK`. Правила целей берутся у самой способности, а поведение —
у её зарегистрированного владельца.

Применение записывается как `GameEvent.Kind.ABILITY_USED` с отдельным каноническим
`Abilities ability`. `abilityId()` возвращает ID, а `isAbility(...)` проверяет
конкретную способность. `SpellState` использует поле `ability` напрямую.
`Abilities.eventTarget()` описывает наличие ID фигуры-цели в истории; эта политика
отличается от геометрии `HeroTargeting`.

`GameEventXml` читает старые имена событий и сохраняет прежнее представление
существующих 24 ID. Новые ID записываются в XML 15 через `kind="ABILITY_USED"`
и `abilityId`; добавлять новые имена в общий enum или адаптер не требуется.

## Проверка

`bash gradlew :composeApp:jvmTest`: **620 тестов**, без падений, ошибок и пропусков
(578 Java + 42 UI). Новые тесты проверяют прежний набор ID, регистрацию enum,
имена констант, отличающиеся от ID, конфликты ID и восстановление скопированного
хука из последовательности событий Ginseng.

Игровые правила, стоимость, кулдауны, подписи и формат сохранений при разделении
способностей не менялись.

В отдельном сравнении версий до и после разделения совпали все 1371 записи
пяти сценариев Пуджа: результаты команд, цели и SHA-256 полных XML-сохранений
после действий и повторной загрузки. Это дополняет общий набор тестов истории,
копирования способностей и совместимости сохранений.

После выделения общего события 24 октября 2026 года проходят **639 тестов**;
дополнительно проверены новые ID, копирование и полное сохранение/восстановление
новой зарегистрированной способности. 1371 запись сценариев и 15 конфигураций
правил совпали с версией до изменения истории.

## Операции специальных механик

`HeroEffect.operations` передаёт неизменяемые данные обработчикам модулей.
`HeroDefinition.mechanics()` объявляет зависимости; контекст предоставляет
состояния через типизированные ключи. Модуль также подключает реакции, проверку
и собственные кодеки состояния/событий. Специальная запись использует
`MECHANIC_EFFECT`, отдельный ID и типизированные данные; новые данные читаются
и записываются общим XML-слоем версии 16. [Контракт механик](MECHANICS.md).

После введения полного запроса проходят **659 тестов** (616 Java + 43 UI), без
падений и пропусков. Новый контракт проверен независимой двухэтапной стратегией,
обеими подсветками, передачей запроса в фазу механики и копией перемещения в UI.
С исходной версией совпали 9249 записей Ginseng, 1371 запись Пуджа, 15
конфигураций правил и 686 записей специальных механик с полными XML-сохранениями.

## Канал применения и стоимость

`AbilityUse(owner, channel)` отделяет владельца правил от настоящего исполнителя.
Оба канала вызывают `Hero.preview(context, request)` стратегии реестра партии.
`AbstractHero` сохраняет специфические ограничения для копий, а собственный
кулдаун и заряд проверяет только при `NATIVE`.

`HeroEffect.withCost(AbilityCost.cooldown(...))` или `ultimate(...)` описывает
расход отдельно от эффекта. База учитывает его один раз до операций механик и
взятий, пропуская для `BORROWED`. Поля фигуры ради копии не подменяются;
`Rules` не обнуляются. `BorrowedEffects` сохранён только как публичный фасад.

Длительные последствия продолжаются после расходования копии. Их модули
объявляют `captureReactions()` и работают с актуальным `DeathContext`.
Освобождение проглоченного союзника перенесено в `SwallowMechanic`.
Пассивки исходного героя не копируются.

Пункт 5 проверен 666 тестами, включая новые зарегистрированные способности,
стоимость, сохранение/загрузку и реакцию новой механики после расходования копии.
С исходной версией совпали 45 570 записей применения прежних копий и 2811
записей результатов, подсветки и полных XML-сохранений после реальных команд.
