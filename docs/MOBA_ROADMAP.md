# План разработки Moba Chess

Обновлено: 16 октября 2026 года.

Актуальные уточнения пользователя записаны в [MOBA_RULES.md](MOBA_RULES.md): один скилл **или** ульта, одно обычное перемещение, применение предметов без общего лимита; способность и перемещение можно выполнить одной фигурой. У фигур минимум обычный скилл и ульта, три слота предметов. Прямой шах от способности запрещён, косвенный разрешён. Закончить ход можно только после одного успешного обычного перемещения; скилл, ульта и предметы необязательны. Завершение выполняется кнопкой «Закончить ход». Git ведёт пользователь; агент его не настраивает и не изменяет. Эти уточнения имеют приоритет над прежними предложениями плана и исходного PDF.

Источник идеи: [Custom Moba-Chess Game.pdf](Custom%20Moba-Chess%20Game.pdf), 5 страниц. Правила и иллюстрации на страницах 2-5 просмотрены. План сопоставлен с [ENGINE.md](ENGINE.md), [TODO.md](TODO.md) и текущими исходниками Java-ядра и Compose Desktop.

Это план следующих изменений, а не описание уже реализованной Moba Chess. Пункты, обозначенные как предложения, требуют решения о правилах. Шахматная основа уже существует; первый прототип Пуджа уже реализован; оставшиеся механики отмечены ниже. Доска остаётся **8×8**. Размеры 10×10 и 16×16 и новые карты отложены согласно предыдущему решению.

## Реализовано в первом прототипе

Добавлены `CLASSIC`/`MOBA`, постоянные ID фигур, `PieceState` с КД/зарядом/тремя слотами, `GameSnapshot`, события, общий лимит скилла/ульты, обязательное обычное перемещение и кнопка завершения с переключением часов. Первый герой - [Пудж-Ладья](PUDGE_ROOK.md): хук по восьми лучам и проглатывание союзника с ответным взятием. Тестовый набор - 218 проверок, включая сценарий через реальный Compose-интерфейс без видимого окна.

Это реализованная часть M02-M04; базовое золото M05 добавлено с Crow; локальный драфт M07 реализован в согласованном упрощённом варианте. Магазин и нейтрал ещё предстоят. Полное сохранение текущего состояния реализовано; инструкция в [SAVE_STATE.md](SAVE_STATE.md). Предметы пока не определены, три слота пустые. Добавлены [пять тестовых позиций](TEST_SCENARIOS.md) с перезапуском. Ульта Пуджа согласована: восемь соседних клеток, заряд за два взятия самим героем, без КД. Временным остаётся КД хука; техническое правило прототипа - свой король безопасен после каждого принятого действия.

## С чего начать

Сначала зафиксировать правила **составного хода и безопасности короля**, затем изменить модель состояния и выполнения действий. В Classic `Game.moveFigure` переключает игрока после перемещения. В реализованном Moba-режиме переключение игрока и часов выполняет `endTurn`. Для схемы «способность или ульта + одно перемещение + применения предметов» этот порядок не подходит. Скилл и перемещение можно выполнить одной фигурой; прежнее ограничение на разные фигуры отменено пользователем.

Первый проверяемый результат: локальная партия на 8×8 с фиксированными тестовыми героями, в которой можно применить способность и сделать обычное перемещение, завершить ход, увидеть перезарядку и получить золото за взятие. Драфт, магазин и нейтрального коня добавлять после того, как этот цикл работает.

### Важные ограничения текущего ядра

- В Classic мат проверяется по обычным перемещениям; в Moba дополнительно проверяются доступные способности Пуджа перед обязательным перемещением. Каталог будущих предметов потребует расширения поиска продолжений.
- `MaterialRules` выводит невозможность мата из обычного материала. Способности, предметы и нейтральная фигура могут изменить такой вывод, в том числе при сдаче и тайм-ауте.
- `PositionValidator` разрешает только стандартные классы, трактует `NONE` как пустую клетку и проверяет ограничения обычных шахмат. Добавление нейтрала и новых превращений требует проверки по выбранному набору правил.
- `Field` создаёт новые объекты фигур; состояние теперь хранится по постоянному ID в `PieceState`. Это правило нужно сохранять для следующих героев и предметов.
- `Figure.points` и `Player.points` не являются кошельком. Сейчас слон стоит 5, ладья 3, ферзь 9; в PDF для экономики указаны другие значения.
- `CellView` показывает базовый шахматный символ и отметку Пуджа. Для нейтрала потребуется отдельное представление; его ещё нет.

## 3. Этап M00. Уточнить правила первой версии

**Зависимости:** нет. **Результат:** короткая спецификация `MOBA_RULES.md` с примерами спорных ситуаций. Таблица ниже перечисляет решения, которые нужны до реализации соответствующего этапа; весь будущий контент заранее придумывать не требуется.

| Вопрос | Что зафиксировать | Предложение для первой версии |
| --- | --- | --- |
| Единицы времени | Что значит ход для перезарядки и возрождения | Различать действие, ход одного игрока и раунд белые + чёрные; не использовать одно поле для всех счётчиков |
| Составной ход | Согласованы обязательное обычное перемещение, необязательный скилл или ульта и необязательные предметы без общего лимита; одна и та же фигура допустима | Явная кнопка «Закончить ход» доступна после успешного обычного перемещения. Способность и предметы для передачи хода не требуются; их эффекты не заменяют обычное перемещение |
| Шах и способности | Согласовано: скилл не даёт прямой шах; изменение положения фигур может дать косвенный шах по обычной геометрии | Безопасность своего короля после каждого действия и проверку мата с учётом доступных способов снять шах ещё нужно согласовать |
| Ничьи и поражение по времени | Пат, повторения, тихие ходы, невозможность мата, соглашение | Вынести в Moba-набор правил. До подтверждения корректности не использовать классический детектор материала как основание Moba-ничьей; отдельно определить исход тайм-аута |
| Драфт | Порядок банов и пиков, ограничения по типам, тайм-аут, кто получает оставшееся право | Сначала простая фиксированная последовательность без скрытых пиков; случайный выбор права и результат фиксируются в событии |
| Начальные герои | Какие клетки можно выбирать, когда расстановка раскрывается | Только свои стартовые клетки соответствующего типа; отдельно решить, видит ли соперник размещение до завершения обоих игроков |
| Способности | Согласованы минимум один обычный скилл и ульта, общий лимит одного применения на ход | Цели, радиус, препятствия, эффект, перезарядка, порог и расход заряда нужно описать для конкретных фигур |
| Иммунитет короля | Иммунитет к вражеским/союзным заклинаниям и косвенным эффектам | Запрет прямого воздействия заклинаний на короля; изменения других фигур по-прежнему могут создавать шах |
| Нейтральный конь | Где появляется, когда ходит, какой атакой оценивает угрозы, что значит 5 ходов | Для прототипа рассмотреть действие после каждого завершённого хода игрока и возрождение через 5 полных раундов; сначала учитывать обычные легальные взятия. Выбор нужно проверить игровыми партиями |
| Предметы и магазин | Согласовано: три слота на фигуру и отсутствие общего лимита применений предметов за ход; каталог пока не задан | Условия повторной активации задаются предметом. Покупка и применение - разные команды; время покупки, передача, продажа и возврат золота требуют отдельных правил |
| Камбэк | Чем считается преимущество и что увеличивается: цена покупки, материал или награда за взятие | Преимущество считать по оставшемуся базовому материалу, а бонус применять к награде за взятие фигур лидера. Исключить пешек-героев, пороги +5/+8 не суммировать повторно |
| Превращение | Когда обычная пешка становится героем, дубликаты, судьба предметов и заряда, жертва без других пешек | Явно описать все ветки, включая конфликт с уникальностью драфта. Не создавать тайное ограничение, исключающее «любого героя» из PDF |
| Шахматные права | Что делают способности с рокировкой, взятием на проходе и пешкой на последней горизонтали | Принудительное перемещение домашней ладьи лишает соответствующего права; срок и отмену взятия на проходе задать для целого хода игрока, а не отдельной команды |

### Радиус из иллюстрации

Зона на странице 4 выглядит как ромб: предполагаемая метрика `abs(rowDelta) + abs(columnDelta) <= radius`. Для радиуса 3 это включает клетку на три шага по прямой, но не клетку со смещением `(2, 2)`. Это вывод по рисунку, который нужно подтвердить. Сам радиус не отвечает на вопрос, должен ли хук идти только по прямой и блокируются ли его цели промежуточными фигурами.

**Готово, когда:** на конкретных позициях можно однозначно ответить, разрешены ли действия, кто ходит следующим, когда изменяется счётчик и когда заканчивается партия. Решения для очередного этапа утверждены до написания его логики.

## 5. Правила проверки при реализации

Для каждого этапа нужны проверки именно нового поведения. Не откладывать проверку взаимодействий до конца.

- **Регрессия Classic:** нынешние шахматные правила, отказ без изменения состояния, синхронизация и часы сохраняются в классическом режиме.
- **Moba-команды:** успешное действие меняет только предусмотренные данные; отказ сохраняет бюджет, ресурсы и случайный выбор, кроме расхода реально прошедшего времени.
- **Взаимодействия:** способности + шах/рокировка/проход; нейтрал + шах/награды/конец партии; превращение + жертва/предметы/уникальность; магазин + очередь/камбэк.
- **Инварианты:** 64 клетки, допустимые объекты и принадлежность, оба короля, согласованные ID и координаты, неотрицательные ресурсы, действительная фаза и права.
- **Воспроизведение:** те же команды и принятые случайные результаты дают тот же снимок; восстановление не даёт лишнее действие, покупку или заряд.
- **Онлайн:** повторы, конкурирующие команды и переподключение не приводят к повторному применению действия или расхождению состояний.

## 7. Первый пакет и дальнейший шаг

1. Записать решения по ходу, шаху, счётчикам и завершению в `MOBA_RULES.md` с 5-10 конкретными примерами.
2. Зафиксировать настройки JDK; Git остаётся в ведении пользователя и не изменяется агентом.
3. Добавить постоянные ID фигур, определения/состояние героев, снимок и события, сохранив классический режим.
4. Реализовать составной ход и его отображение: общий лимит скилла/ульты, одно перемещение с возможностью той же фигуры, три слота и отдельная активация предметов без общего лимита. Сначала использовать одну тестовую способность и пустой каталог предметов.

Это первый объём, который стоит начинать после согласования правил. Сроки и размер команды пока не заданы, поэтому план фиксирует зависимости и критерии результата, а не неподтверждённые календарные оценки.

Первый пакет ID/составного хода/героя реализован в объёме запроса пользователя. Ближайшая проверка - сыграть Пуджем, уточнить временные параметры и описать следующий герой или первые предметы. Золото из M05 остаётся следующим самостоятельным этапом.
